⚡ Why Errors Happen During Transmission

Data is sent as electrical signals, light, or radio waves. Interference can disturb the signal so that it is read incorrectly. This can cause:

  • Data loss — bits that were sent never arrive.
  • Data gain — extra bits arrive that were never sent.
  • Data change — bits arrive with the wrong value (a 1 instead of a 0, or the other way round).

Common causes of interference

  • Electrical interference from nearby equipment
  • Power surges
  • Synchronisation issues
  • Wear and tear on the cable or connectors
  • A weak wireless signal
Why this is dangerous: The received data usually still looks like valid data. Without an error check, the receiver would not know anything was wrong. A single wrong bit can change a letter, a number in a bank payment, or an instruction in a program.

1️⃣ Parity Check

In a parity check, the sender and receiver agree to use either even or odd parity. The sender adds a parity bit to each byte so that the number of 1s is even (even parity) or odd (odd parity). The receiver counts the 1s in each byte; if the count is wrong for the agreed parity, an error has occurred.

The process

  1. The sender and receiver agree whether to use even or odd parity.
  2. For each byte, the sender counts the 1s in the 7 data bits and sets the parity bit to 0 or 1, so that the total number of 1s (including the parity bit) is even (or odd).
  3. The byte is transmitted.
  4. The receiver counts the 1s in the byte it receives.
  5. If the total does not match the agreed parity, an error has occurred, and the byte is sent again.
Key idea: For even parity, all the 1s (including the parity bit) must add up to an even number. For odd parity, all the 1s must add up to an odd number.

Limitations of a parity check

  • If an even number of bits are changed (such as two), the number of 1s stays even (or odd), so the error is not detected.
  • A parity check on a single byte shows that an error has happened, but not which bit is wrong.

2️⃣ Parity Block Check

A parity block check sends data in a block of bytes. Each byte has its own parity bit, checking each row. An extra byte — the parity byte — is added at the end: each of its bits is the parity bit for one column of the block.

If a single bit is changed, one row and one column will both fail their parity check. The wrong bit is where that row and column cross, so the receiver can find it, and even correct it, without the block being sent again.

Why this is powerful: A plain parity check can only tell you that an error happened. A parity block check can tell you where it happened — and if only one bit is wrong, it can be corrected on the spot.

3️⃣ Checksum

A checksum is a value calculated from a block of data using an agreed algorithm. The sender calculates the checksum and sends it with the data. The receiver recalculates the checksum from the data it received; if the two checksums do not match, an error has occurred.

The process

  1. Before sending, the sender uses an agreed algorithm to calculate a checksum from the block of data.
  2. The checksum is transmitted along with the data.
  3. The receiver uses the same algorithm to recalculate the checksum from the data it received.
  4. The receiver compares the two checksums. If they match, the data is accepted. If they are different, an error has occurred, and the data is sent again.

4️⃣ Echo Check

In an echo check, the receiver sends a copy of the data it received straight back to the sender. The sender compares this copy with the original data. If they are different, an error has occurred, and the data is sent again.

Worked walkthrough: An echo check

  1. The sender transmits the data, 10110110, and keeps a copy of it.
  2. Interference changes one bit on the way, so the receiver gets 10110010. The receiver does not know this.
  3. The receiver sends an exact copy of what it received back to the sender: the "echo".
  4. The sender now has its original data and the echo.
  5. The sender compares them. They are different, so an error has occurred, and the sender transmits the data again.
Limitations of an echo check:
  • Every piece of data is sent twice, so it takes more time and uses more bandwidth.
  • If the copies differ, the sender cannot tell whether the error happened on the way to the receiver or on the way back. The data is sent again either way.

5️⃣ Check Digits

A check digit is an extra digit added to the end of a number, calculated from all the other digits. It is used to detect errors when the number is entered (typed in or scanned). The computer recalculates the check digit from the digits entered; if it does not match the check digit, an error has been made.

Errors in data entry

Check digits are designed to catch the mistakes people commonly make when entering a long number:

  • Typing one digit incorrectly (e.g. 5 instead of 8)
  • Swapping two digits round (e.g. 45 instead of 54 — a transposition error)
  • Missing out a digit, or typing an extra one

Where check digits are used

  • International Standard Book Numbers (ISBNs) — the 13-digit number that identifies every published book. The last digit is the check digit.
  • Barcodes on products — the number under the barcode ends with a check digit, which detects errors when the barcode is scanned or the number is typed in by hand.
  • Other examples include bank card numbers and some identity numbers.

Try it: Checking an ISBN

In this algorithm, the digits are multiplied by 1 and 3 in turn, and the products are added up. The check digit is whatever is needed to bring the total up to the next multiple of 10. Try the example, then change a digit to see the check fail.

Check digits and validation: A check digit is also one of the validation checks, because it is carried out automatically by the computer when data is entered. It is different from verification checks (such as double entry), which compare the data with a second copy of it.

6️⃣ Automatic Repeat Query (ARQ)

An automatic repeat query (ARQ) uses acknowledgements and a timeout to make sure data is received without error. The receiver checks each packet and replies with a positive acknowledgement if it is correct, or a negative acknowledgement if it is not. If the sender receives a negative acknowledgement, or no acknowledgement before the timeout, it sends the data again.

The process

  1. The sender transmits a packet of data, including an error check such as a checksum, and starts a timer.
  2. The receiver uses the error check to see whether the packet has arrived correctly.
  3. If there is no error, the receiver sends back a positive acknowledgement (ACK), and the sender moves on to the next packet.
  4. If there is an error, the receiver sends back a negative acknowledgement (NACK), and the sender sends the packet again.
  5. If the sender receives no acknowledgement before the timer reaches the set time limit (the timeout), it assumes the packet was lost and sends it again automatically.
  6. This repeats until a positive acknowledgement is received.

📊 Comparing the Methods

Method Used for How the error is found
Parity check Transmission The number of 1s in a byte does not match the agreed odd or even parity
Parity block check Transmission A row and a column fail their parity checks, pinpointing the wrong bit
Checksum Transmission The recalculated checksum does not match the one sent
Echo check Transmission The data echoed back is different from the original
Check digit Data entry The recalculated check digit does not match the one entered
ARQ Transmission A negative acknowledgement is received, or no acknowledgement arrives before the timeout
