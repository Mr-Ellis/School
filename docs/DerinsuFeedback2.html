! The biggest mistakes you could make

❌ Thinking the implementation section is finished
Your implementation discussions are already stronger than many IB examples. The main weakness is not the implementation discussion — it is the absence of strong testing evidence. A moderator is more likely to deduct marks for insufficient abnormal tests, insufficient extreme tests and a lack of actual results than for implementation choices.
❌ Writing more code explanations
Avoid expanding descriptions such as “The route inserts the record into the database” or “The SQL query retrieves clients.” Moderators do not award many marks for additional code explanation. Instead add:
  • Testing evidence
  • Testing outcomes
  • Testing limitations
  • Screenshots
  • Demonstration evidence
❌ Assuming automated tests automatically score highly
A common IB misconception. Moderators reward evidence of effective testing, not the existence of tests. Eight automated tests sound good, but moderators must see what those tests prove.

2 Structure for each technique

Use this exact structure for every technique. Point F is evaluation, point H is testing justification — both are what the top band rewards.

A
What is the technique?
“Appointment overlap detection is a boundary-checking algorithm that compares the start and end times of a proposed booking against existing bookings.”
B
How is it used in my solution?
“Every new booking is checked against all existing bookings for the same instructor before it is saved.”
C
Why did I choose it?
“Overlapping bookings would cause double-booking, which is a real-world failure of a studio management system.”
D
What alternative could I have used?
“A simple string comparison of time slots would have been faster to write, but it would fail on partially overlapping bookings.”
E
What is a limitation?
“The algorithm assumes each instructor cannot be in two places at once, which may not hold for multi-room studios.”
F
Why is my choice still appropriate? (evaluation)
“Although it adds a query per booking, the cost is small compared with the cost of a double-booking.”
G
How did I test it?
“I tested valid bookings, back-to-back bookings, overlapping bookings and bookings that share only an endpoint.”
H
Why was the testing effective?
“The abnormal tests proved that the algorithm rejects partial overlaps, and the boundary tests proved that back-to-back bookings are still accepted.”
I
What does the testing NOT prove?
“The tests confirm correct behaviour on the cases I tried, but not that the algorithm scales to hundreds of bookings per instructor.”
