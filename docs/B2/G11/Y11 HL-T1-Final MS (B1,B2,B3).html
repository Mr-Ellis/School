Section A — Programming Fundamentals (26 marks)

1. Definitions & scope[4]
[1] A variable is a named storage location whose value can change during execution.
[1] A constant is a named storage location whose value is assigned once and cannot be changed while the program runs.
[1] Local scope: a variable declared inside a function is visible only within that function; it is created on call and destroyed on return.
[1] Global scope: a variable declared outside all functions is visible throughout the program and persists for the program's lifetime.
2. Analyse try–except–finally[6]
[1] First call safe_divide(10, 2): returns 5.0; finally prints "Calculation complete"; x = 5.0.
[1] Second call safe_divide(10, 0): raises ZeroDivisionError; the handler prints "Cannot divide by zero" and returns None; finally still prints "Calculation complete"; y = None.
[1] Third call safe_divide("10", 2): raises TypeError (cannot divide a string); the handler prints "Invalid input type" and returns None; finally still prints "Calculation complete"; z = None.
[1] The finally block always executes, whether the try block succeeds or an exception is raised.
[1] The two except clauses are specific, so each exception is matched to a handler that describes the actual problem.
[1] Because the exceptions are caught, the program continues executing all three calls; without handling, the first error would have terminated the program.
3. Exception order[3]
[1] Python checks except clauses in order and executes the first matching one.
[1] If a general except Exception appears first, it catches everything (since every specific exception is a subclass of Exception), so the specific handlers below it are unreachable.
[1] Consequence: the program cannot respond to specific errors precisely — a ZeroDivisionError would be reported as a generic error, losing the chance to display a targeted message.
4. Evaluate debugging techniques[6]
[1] Trace table: manually step through the code, recording each variable's value after each line, to find where the output diverges from expectations.
[1] Advantage of a trace table: no tools required, works on paper, and forces the programmer to reason about the algorithm line by line — good for short programs.
[1] Breakpoint debugging: pause the program at a chosen line in an IDE, inspect all variable values, and step line by line through execution.
[1] Advantage of breakpoint debugging: shows the actual runtime state of a large program quickly, without instrumenting the code; effective when the error involves complex data structures or many variables.
[1] Comparison: for short algorithms, a trace table is often faster because it requires no setup and documents the reasoning; for larger programs with many variables, breakpoints are more efficient because inspecting runtime state is faster than manually tracking dozens of values.
[1] Justified conclusion: the trace table is more effective for understanding why the logic is wrong, while breakpoints are more effective for locating where a value becomes wrong — so the best choice depends on whether the programmer needs explanation or localisation.
5. Strings & password check[4]
[1] Concatenation joins strings with +; e.g. "pass" + "word" gives "password".
[1] Slicing extracts a substring with string[start:end] (start included, end excluded); e.g. "password"[0:4] gives "pass".
[1] Length check: if len(password) >= 8:
[1] Character check: if "@" in password: (combined with the length check using and to require both).
6. Instruction order[3]
[1] A program is a sequence of instructions; changing the order changes the logic, because later instructions depend on the effects of earlier ones.
[1] Example: computing average = total / count before the loop that fills total runs gives an average of 0, not the real value — both versions are syntactically valid.
[1] Only the version that initialises, then loops, then computes satisfies the intended input–process–output transformation.

Section B — Data Structures (30 marks)

7. Static vs dynamic comparison[4]
[1] Memory location: static → stack; dynamic → heap.
[1] Allocation time: static → compile time; dynamic → runtime.
[1] Access speed: static → fast, direct O(1); dynamic → slower, may require traversal O(n).
[1] Flexibility: static → fixed size, cannot resize; dynamic → grows and shrinks as needed.
8. Justify data structure for hospital records[5]
[1] A static array requires a fixed size chosen in advance.
[1] If sized too small, the array overflows when patient records exceed capacity — unacceptable in a hospital.
[1] If sized too large, memory is wasted permanently.
