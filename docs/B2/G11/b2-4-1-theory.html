The Big Idea

Imagine two delivery drivers going to the same city. One takes a direct motorway route; the other drives through every small town on the way. Both arrive eventually — but the first driver gets there in a fraction of the time. In computing, the route is the algorithm, and efficiency is about how well that route scales as the journey gets longer.

Big O notation is the language we use to describe how an algorithm's running time (or memory use) grows as the input size increases. It doesn't tell us the exact number of seconds — it tells us the shape of the growth curve. This is crucial for scalability: an algorithm that feels instant on 100 items might grind to a halt on 10 million.

📚 Further reading: Course companion pages 386–390. See also the Computer Science Wiki page on Big O notation.

💡 Think of Big O like classifying vehicles by top speed: O(1) is a rocket (instant, regardless of distance), O(log n) is a bullet train (very fast, barely slows as distance grows), O(n) is a car (time grows in direct proportion to distance), and O(n²) is a bicycle that gets slower and slower the further you go. We care about the class of vehicle, not the exact speedometer reading.

1. What is Algorithm Efficiency?

Efficiency is a measure of the resources an algorithm consumes — primarily time (how many operations it performs) and space (how much memory it uses). When we analyse efficiency, we are not measuring wall-clock seconds (which depend on hardware, programming language, and compiler), but rather the number of basic operations as a function of input size n.

Why not just time it with a stopwatch?

  • A faster computer would make the same algorithm look better — that tells us nothing about the algorithm itself.
  • Small inputs hide inefficiencies; an O(n²) algorithm may beat an O(n log n) one for n = 10, but lose catastrophically for n = 1,000,000.
  • We need a hardware-independent way to compare algorithms and predict their scalability.

Time Complexity vs Space Complexity

💡 Think about it: Google processes billions of searches per day. If the search algorithm were O(n) in the number of web pages, adding more pages would slow it down proportionally — unacceptable. Algorithms must be designed to scale. Similarly, a social network's "friend recommendation" algorithm that is O(n²) may work for a small user base but become impossibly slow when millions of users join. Big O lets engineers predict these problems before they deploy.

2. Big O Notation: The Language of Growth

Big O notation describes the upper bound on an algorithm's growth rate — that is, the worst-case scenario as input size n becomes very large. Formally, we say f(n) = O(g(n)) if there exist constants c and n₀ such that f(n) ≤ c · g(n) for all n ≥ n₀. In practice, this means we drop constants and lower-order terms.

The simplification rules

  • Drop constants: O(3n) → O(n); O(0.5n²) → O(n²).
  • Keep only the dominant term: O(n² + n + 5) → O(n²).
  • Ignore the base of logarithms: O(log₂ n) and O(log₁₀ n) are both written O(log n).

Why? Because as n gets huge, the highest-order term dominates everything else. For n = 1,000,000, n² is a trillion while n is a million — the linear term is negligible in comparison.

🔍 Big O is about the worst case: When we say "linear search is O(n)", we mean that in the worst case (the item is last or absent), it examines every element. Big O gives us a guarantee: "this algorithm will never be slower than this class."

⚠️ Watch out: An O(n²) algorithm may be faster than an O(n log n) algorithm for tiny inputs (because of smaller constants). Big O describes asymptotic behaviour — how it scales as n → ∞. For small n, the constants can matter. This is why real-world sorting libraries sometimes use insertion sort for tiny subarrays and quicksort for large ones.

💡 Think about it: A logarithm asks "how many times can I divide n by 2 before I get to 1?" For n = 1,000,000, that's about 20. So an O(log n) algorithm does roughly 20 steps for a million items. That's why binary search is so powerful: each comparison eliminates half the remaining possibilities. Doubling the input size adds only one extra step — that's extraordinary scalability.

4. Analysing Specific Algorithms

Linear Search — O(n)

Linear search checks each element from the start until it finds the target (or reaches the end). In the worst case, it examines every element once.

def linear_search(arr, target):
    for i in range(len(arr)):
        if arr[i] == target:
            return i
    return -1

Analysis: The loop runs at most n times, and each iteration does a constant amount of work. Total: O(n).

Binary Search — O(log n)

Binary search works on a sorted array. It compares the target with the middle element, then discards the half that cannot contain the target. Each step halves the search space.

def binary_search(arr, target):
    low, high = 0, len(arr) - 1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1

Analysis: After k iterations, the remaining search space has size n / 2ᵏ. The loop stops when n / 2ᵏ ≤ 1, i.e. k ≈ log₂ n. Total: O(log n).

💡 The power of halving: For an array of 1,000,000 sorted items, linear search needs up to 1,000,000 comparisons. Binary search needs at most 20. That's a 50,000× improvement — a direct consequence of moving from O(n) to O(log n).

Bubble Sort — O(n²)

Bubble sort repeatedly steps through the list, compares adjacent pairs, and swaps them if they're in the wrong order. It repeats this until no swaps are needed.

def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        for j in range(n - 1 - i):
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]

Analysis: The outer loop runs n times. The inner loop runs roughly n times for each outer iteration. Total comparisons ≈ n · n = n². Total: O(n²).

Merge Sort — O(n log n)

Merge sort divides the array in half, recursively sorts each half, and then merges the sorted halves together. The dividing takes log n levels, and each level does O(n) work to merge.

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return merge(left, right)   # merge is O(n)

Analysis: There are log n levels of recursion, and at each level the total work across all subproblems is O(n). Total: O(n log n).

5. Calculating Big O: A Step-by-Step Guide

When asked to calculate the Big O of a piece of code, follow these steps:

  1. Identify the loops: How many times does each loop run relative to n?
  2. Nested loops multiply: A loop inside a loop gives O(n × n) = O(n²).
  3. Sequential loops add: Two separate loops give O(n + n) = O(2n) → drop constants → O(n).
  4. Drop constants and lower-order terms: O(3n² + 5n + 7) → O(n²).
  5. Halving loops are logarithmic: If a loop variable doubles/halves each iteration, it's O(log n).

Worked example

def example(arr):
    n = len(arr)
    total = 0
    for i in range(n):          # loop 1: O(n)
        total += arr[i]
    for j in range(n):          # loop 2: O(n)
        for k in range(n):      # nested inside loop 2: O(n)
            total += arr[j] * arr[k]
    return total

Analysis: Loop 1 contributes O(n). The nested loops contribute O(n²). Total: O(n + n²) → dominant term is n² → O(n²).

📝 Exam tip: Always look for nested loops first — they're the most common source of O(n²). If you see a loop where the counter is halved (i = i / 2 or i *= 2), that's a strong sign of O(log n). If the algorithm divides the problem and processes both halves, think O(n log n).

Question 1 (2 marks)

Define the term Big O notation and explain what it is used for.

Big O notation is a mathematical notation used to describe the upper bound on the growth rate of an algorithm's time or space complexity as the input size increases. It is used to compare algorithms independently of hardware and to predict how well an algorithm will scale for large inputs.

Question 2 (3 marks)

Explain why an O(log n) algorithm is considered more efficient than an O(n) algorithm. Use an example to support your answer.

An O(log n) algorithm's running time grows very slowly as input size increases, because it typically halves the problem at each step. An O(n) algorithm's time grows in direct proportion to the input. For example, for 1,000,000 items, a linear search (O(n)) needs up to 1,000,000 comparisons, while binary search (O(log n)) needs at most about 20. Doubling the input size adds only one extra step for O(log n), but doubles the work for O(n).

Question 3 (4 marks)

Analyse the time complexity of the following algorithm and justify your answer:

def find_pairs(arr):
    n = len(arr)
    count = 0
    for i in range(n):
        for j in range(i + 1, n):
            if arr[i] == arr[j]:
                count += 1
    return count

The algorithm has two nested loops. The outer loop runs n times. The inner loop runs from i + 1 to n - 1, which is roughly n/2 iterations on average. The total number of comparisons is n × (n - 1) / 2, which is proportional to n². Therefore, the time complexity is O(n²).

Marks: 1 for identifying nested loops; 1 for explaining the inner loop runs roughly n times for each outer iteration; 1 for stating total operations ≈ n²/2; 1 for simplifying to O(n²) by dropping constants.

Question 4 (3 marks)

Explain the difference between time complexity and space complexity. Give one example of each from an algorithm you have studied.

Time complexity measures how the number of operations grows with input size; space complexity measures how memory usage grows. Example of time complexity: bubble sort has O(n²) time complexity because of its nested loops. Example of space complexity: merge sort has O(n) space complexity because it creates temporary arrays during merging, while bubble sort has O(1) space complexity because it sorts in place.
