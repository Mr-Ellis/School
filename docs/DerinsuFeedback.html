2. How to Write Each Technique

Aim for 100 words per technique, using the same five-point structure:

  1. What the technique is
  2. Where in your code it appears
  3. Why you chose it
  4. What benefit it gives the user
  5. What limitation it has

Point five is what most students skip. It is also what turns a description into an evaluation, which is what the top band requires.

5. Required Code Changes

5.1 The executable does not open — Ordinal Not Found error

The executable has been built, but it does not open. The error shown when launching it is:

PilatesStudioManager.exe - Ordinal Not Found
The ordinal 380 could not be located in the dynamic link library
...\PilatesStudioManager.exe.

This is not a bug in the Python code. It is a Windows error that occurs when a packaged executable cannot find a system DLL function it depends on. The most common causes and fixes are:

  • Missing Visual C++ Redistributable. Python depends on the Microsoft Visual C++ runtime. If the machine running the .exe does not have the correct version installed, the .exe fails with this exact error. Fix: install the latest Visual C++ Redistributable (x64) on the machine where the .exe is being run.
  • The build was made with a mismatched Python version. PyInstaller-built executables are tied to the Python version they were built with. If the .exe was built on one machine and run on another with a different runtime, this error appears. Fix: rebuild the executable on the same machine it will be run on, using the same Python version.
  • PyInstaller was run with --onefile. --onefile produces a single .exe that extracts itself at runtime, and this can trigger Ordinal Not Found errors on some systems. Fix: rebuild with --onedir instead, which produces a folder containing the .exe and its dependencies. Onedir is more reliable for Flask + webview apps.
  • Antivirus interference. Some antivirus programs block the extraction step. Fix: add an exception for the folder.

The recommended rebuild command using onedir:

pip install pyinstaller
pyinstaller --onedir --windowed --name "PilatesStudioManager" PilatesStudioManager.py

Notes:

  • --onedir is more reliable than --onefile for Flask + webview apps, because the app loads several libraries at runtime
  • --windowed hides the console window, correct for a GUI-only app
  • The Flask templates/ folder must be copied next to the .exe, or added to the build with --add-data "templates;templates"
  • Test the rebuilt folder on a machine that does not have Python installed

Once the executable opens, record it as a technique in the Criterion D write-up — this is one of the strongest pieces of evidence for a "fully functional product".

5.2 Confirm the SQLite path works after packaging

Your get_database_path() function writes the database to %LOCALAPPDATA%\PilatesStudioManager\studio.db on Windows. This is the correct approach — it avoids trying to write inside Program Files where permissions are restricted. Confirm after packaging that the database file is actually created in that folder when the app runs. Screenshot the folder in the video.

5.3 Add a splash / welcome screen

The current home page shows client and session counts, which is a good landing view. Add a short welcome block on first launch explaining what the app does. The simplest approach is a dismissible banner at the top of home.html that disappears after the user clicks a "Got it" button, or a first-run message shown only when client_count == 0 and session_count == 0. This supports SC9 (usability) and gives you a screenshot for the Criterion C wireframe.

5.4 Note the pagination limitation

The clients page loads every client in one view. With Maria's current load of 20 clients, this is fine. If the studio grows, the page will become slow. Note this as a known limitation in the write-up, and mention that pagination or a lazy-loading table would be the fix. This is the kind of evaluation the rubric asks for.

5.5 Document why SQLite was chosen over MySQL

Your Criterion A says you will use MySQL. Your implementation uses SQLite. The rubric requires development to be consistent with planning. Two options:

  • Option A: Update Criterion A to say SQLite, and justify the change (no server to install, runs on the client's laptop without any setup, file-based so it moves with the app).
  • Option B: Refactor to MySQL. This would require the client to install and run a MySQL server, which is against the "simple for Maria" goal stated in Criterion A. Option A is strongly recommended.

The switch from MySQL to SQLite is a deliberate improvement, not a mistake. State it clearly in the Criterion D write-up.

5.6 Document the reason for a Flask + webview architecture

Your Criterion A describes a Python application but does not explain why a Flask web app inside a native window was chosen over a native GUI like Tkinter or PyQt. This is a significant architectural choice and deserves a paragraph in the write-up. Points to make:

  • HTML/CSS gives a much cleaner visual layout with less code than Tkinter
  • The same code could be served over the network later if Maria wants a second device
  • pywebview hides the browser chrome so it still feels like a desktop app
  • Limitation: the app has a small local web server running inside it, which is heavier than a pure native app

7. Splash Screen

A splash screen supports SC9 and provides a screenshot for the Criterion C wireframe. Since this is a web app, the easiest approach is a dismissible banner on the home page. Keep it short.

7.1 Where to add it

In home.html, add a banner block at the top that is only shown when both client_count == 0 and session_count == 0 (first run), or when the user has not yet dismissed it. Pass a flag from the home() route if you want it re-displayable.
