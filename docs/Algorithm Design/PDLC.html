In this topic, we will look at the Waterfall Development model, which forms the basis of the Program Development Life Cycle (PDLC) in the IGCSE specification: Analysis → Design → Coding → Testing.

🎯 Learning Objectives

  • Describe the tasks in each stage:
    • Analysis – abstraction, decomposition, problem identification, requirements.
    • Design – decomposition, structure diagrams, flowcharts, pseudocode.
    • Coding – writing program code and iterative testing.
    • Testing – testing program code with test data.
Why This Matters: Following a structured life cycle helps developers build software that meets requirements, reduces errors, and is easier to maintain. Mistakes are cheapest to fix early — a misunderstanding spotted during analysis takes minutes to fix, but the same mistake found after the program is finished may mean rewriting large parts of it. This is a core topic in the IGCSE Computer Science syllabus.

🔁 The Four Stages of the PDLC

The program development life cycle (PDLC) is the series of stages followed to develop a program: analysis, design, coding and testing. Working through them in order means the problem is understood before it is solved, the solution is planned before it is written, and the program is checked before it is used.

Stage Question it answers What happens What it produces
1. Analysis What is the problem, and what must the program do? The problem and its requirements are identified, using abstraction, decomposition and identification of the inputs, processes and outputs. A clear list of requirements
2. Design How will the program work? The solution is planned using decomposition, structure diagrams, flowcharts and pseudocode. Structure diagrams and algorithms
3. Coding How do we build it? The program code is written, and each part is tested as it is written (iterative testing). A working program
4. Testing Does it work? The complete program is run with test data, and the actual results are compared with the expected results. Evidence that the program meets its requirements
Why it is called a cycle: The stages are not always completed once, in a straight line. If testing shows that the program gives a wrong result, the developer goes back to coding to fix the error, or back to design if the algorithm itself is wrong. If the requirements were misunderstood, the work goes back to analysis. The stages are repeated until the program works as required.

1️⃣ Analysis

Analysis is about understanding the problem fully before trying to solve it. It answers the question: "What is the problem, and what must the program do?"

Identifying the Problem & Requirements

A requirement is something the finished program must do. They are found by investigating the problem, for example by talking to the people who will use the program. They must be clear and specific, because they are used later to check whether the program works.

Key idea: Requirements only state what the program must do, never how it will be done. The "how" is decided in the Design stage.

Worked Example: Quiz Program Requirements

  • The program must allow a score to be entered for each of the 30 students.
  • Each score must be a whole number from 0 to 20.
  • The program must reject any score outside this range and ask for it again.
  • The program must output the highest score.
  • The program must output the class average.

Abstraction

Abstraction means removing details that are not needed to solve the problem, so that only the key elements are kept. It makes the problem simpler and keeps the program focused on what matters. What counts as "unnecessary" depends on the requirements.

Decomposition

Decomposition means breaking a complex problem down into smaller, more manageable parts. Each part is easier to understand and solve on its own, different people can work on different parts, and each part can be tested separately.

Identifying Inputs, Processes, Outputs and Storage

Every program takes in data (inputs), does something with it (processes), and produces results (outputs). It may also need to keep data while it runs or for later (storage).

Inputs Processes Outputs Storage
30 quiz scores, each a whole number from 0 to 20 Check each score is in range; add each score to a running total; compare each score with the highest so far; divide the total by 30 The highest score; the class average; an error message when a score is invalid The running total; the highest score so far

2️⃣ Design

In design, the solution is planned before any code is written. The problem is decomposed into sub-systems and shown as a structure diagram, and the steps of the solution are written as algorithms using flowcharts or pseudocode.

Structure Diagrams

A computer system is made up of sub-systems, and each sub-system can be broken down further. A structure diagram shows this breakdown from the top down: the whole system at the top, with each level below showing more detail.

Key distinction: A structure diagram shows what the parts of a system are. It does not show decisions, loops or the exact order of steps; that is what flowcharts and pseudocode are for.

Flowcharts

A flowchart shows the steps of an algorithm using standard symbols joined by arrows (flow lines).

BEGIN

Terminator (Start/End)

INPUT age

Input/Output

Total = A + B

Process

age > 18?

Decision

Interactive: Trace the Flowchart

Look at this logic:
BEGIN ➔ INPUT age ➔ Is age > 18? ➔ YES: OUTPUT "Adult" ➔ END.
NO: OUTPUT "Child" ➔ END.

Question: If the user inputs exactly 18, what is the output?

Pseudocode

Pseudocode describes an algorithm in structured, English-like statements that do not belong to any one programming language.

Pseudocode C# (Real Code) 
FOR i < 0 TO 10
    OUTPUT i
NEXT i
 
for (int i=0; i<10; i++) {
    Console.WriteLine(i);
}
Why design before coding?
  • Mistakes in the logic can be found and corrected before any time is spent writing code.
  • The design is a guide for the programmer, or for several programmers each writing a different part.
  • An algorithm in pseudocode or a flowchart can be coded in any programming language.

3️⃣ Coding

In coding, the design is turned into program code in a programming language. Each part is tested as soon as it has been written, and any errors are fixed before moving on. This is called iterative testing.

Iterative Testing

  • Write one part (module) of the program.
  • Test it with suitable test data.
  • If there is an error, fix it and test the part again.
  • Repeat until the part works, then move on to the next one.

Scenario: The Quiz Score Bug

A programmer writes the code to check if a student's quiz score is valid. Valid scores are between 0 and 20.

They write this condition: IF score > 21 THEN...

Question: If a student enters a score of 21, will the program accept or reject it based on the code?

Why test iteratively?
  • Errors are easier to find in a few new lines than in a whole program.
  • Each part is known to work before it is combined with the others.
  • Problems are not left to build up until the end, when they are harder and slower to fix.

4️⃣ Testing

In the testing stage, the complete program is run with carefully chosen test data to check that it works correctly and meets every requirement identified in analysis. For each test, the actual result is compared with the expected result.

Types of Test Data

Type What it is Should the program accept it?
Normal Valid data within the expected range Yes
Abnormal Invalid data: outside the range or the wrong type No
Extreme The largest and smallest valid values Yes
Boundary The values either side of each limit: the last value accepted and the first value rejected One of each pair is accepted and the other rejected

When a test fails: A failed test sends the work back round the cycle. If a test shows the program crashes when given text instead of a number, the developer goes back to design to add a type check, then codes it and runs all the tests again. This is why the PDLC is a cycle: each time round, the program gets closer to meeting all of its requirements.
