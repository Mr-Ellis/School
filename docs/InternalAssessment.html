A

📋 Criterion A Problem Specification

4 marks · 300 words

Define a genuine real-world problem with a clear stakeholder, testable success criteria, and a justified computational context.

  • Problem Scenario — real stakeholder, measurable requirements, clear need
  • Success Criteria — testable, specific, define a complete solution
  • Computational Context — justify why each technology solves the problem

Criterion A: Moderator Mark Bands

These boundaries are derived from official moderated examples. Moderators look for specific evidence in the Problem Scenario, Success Criteria, and Computational Context.

To Reach 2/4
  • ✔ Describe a problem
  • ✔ State some success criteria
  • ✔ Mention tools/language
  • ✘ Requirements may be unclear
  • ✘ Context may be weak
  • ✘ Stakeholder may be underdeveloped
To Reach 3/4
  • ✔ Clear stakeholder
  • ✔ Clear problem
  • ✔ Some measurable requirements
  • ✔ Mostly appropriate success criteria
  • ✔ Some explanation of technology choices
  • ✘ But one strand is still noticeably weak — e.g. vague criteria, too few criteria, generic computational context
To Reach 4/4
  • ✔ Real stakeholder & real need
  • ✔ Several measurable requirements
  • ✔ Success criteria define a complete solution
  • ✔ All criteria testable
  • ✔ Technologies explicitly justified
  • ✔ Every technology linked to solving part of the problem
  • ✘ "I chose Python because I know Python."
    ✔ "I chose Python because Pygame provides collision detection, game loops and event handling required for the Flappy Bird mechanics."
⚡ Ultimate Criterion A rule: The difference between 3/4 and 4/4 is usually not the success criteria — it's whether the problem scenario and computational context are convincing, specific, and clearly connected to the solution.

B

📐 Criterion B Planning

4 marks · 150 words

Decompose the problem and create a plan that directly addresses your success criteria from Criterion A.

  • Decomposition — clear diagrams breaking the system into components
  • Plan — GANTT/AGILE showing how each success criterion will be met
  • Must be consistent with Criterion A

Criterion B: Moderator Mark Bands

Your planning must explicitly reference the success criteria defined in Criterion A. Moderators look for a clear mapping between the problem decomposition and the timeline.

To Reach 2/4
  • ✔ Some decomposition shown
  • ✔ A basic plan exists
  • ✘ Plan may not clearly address success criteria
  • ✘ Decomposition may be shallow or generic
To Reach 3/4
  • ✔ Clear decomposition of the problem
  • ✔ Plan addresses most success criteria
  • ✔ Reasonable timeline / task breakdown
  • ✘ But one area is noticeably weak — e.g. plan is generic, or decomposition misses a component
To Reach 4/4
  • ✔ Thorough decomposition with clear diagrams
  • ✔ Plan explicitly maps to each success criterion
  • ✔ Realistic timeline with dependencies
  • ✔ Plan is consistent with Criterion A
⚡ Ultimate Criterion B rule: Your plan must map back to the success criteria — moderators check this explicitly. A generic GANTT that doesn't reference your specific criteria won't reach the top band.

C

🧩 Criterion C System Overview

6 marks · 150 words

Produce a complete system model, algorithms for major functionality, and a rigorous testing strategy aligned to your success criteria.

  • System Model — UI design, UML (OOP), architecture, data structures, storage
  • Algorithms — major features represented, linked to system model
  • Testing Strategy — success criteria, expected outcomes, valid/extreme/invalid data

Criterion C: Moderator Mark Bands

Criterion C is judged by omissions, not volume. A 15-page document can still score 4/6 if UI design, UML, or extreme/invalid testing data is missing.

To Reach 1–2/6
  • ✔ One simplistic diagram
  • ✔ Little algorithmic detail
  • ✘ No structured testing
  • ✘ Major parts of the solution undocumented
  • ✘ A programmer could not understand how the solution works
To Reach 3/6
  • ✔ System model is minimal (often one diagram)
  • ✔ Functional algorithms may exist but coverage is limited
  • ✘ Testing is demonstration-oriented, no structural testing
  • ✘ No valid/extreme/invalid test data
To Reach 4/6
  • ✔ Multiple diagrams present
  • ✔ UI and/or UML may be present
  • ✔ Algorithms mostly functional
  • ✔ Testing aligned with success criteria
  • ✘ Important omissions remain — e.g. missing UI design, incomplete algorithms, weak structural testing
  • ✘ Often does not consider extreme or abnormal data
To Reach 5/6
  • ✔ UI designs, UML, architecture, data structures, storage structures
  • ✔ Major system components documented
  • ✔ Clear, detailed algorithms supporting major functionality
  • ✔ Testing aligned with success criteria and expected outcomes
  • ✘ Some weaknesses remain — e.g. missing file interactions, incomplete modelling, testing limitations
To Reach 6/6
  • ✔ Comprehensive system model — no significant omissions
  • ✔ Every major feature represented algorithmically
  • ✔ Direct relationship between algorithms and system components
  • ✔ Functional and structural testing
  • ✔ Valid, extreme and invalid data with expected outcomes
  • ✔ A competent programmer could reconstruct the solution from Criterion C alone
⚡ Ultimate Criterion C rule: Criterion C is judged more by omissions than by volume. A 15-page Criterion C can still receive 4/6 if important parts are missing. Testing is the most common reason students lose marks — a demonstration script is not a testing strategy.

D

💻 Criterion D Development

12 marks · 1,000 words

Build a fully functional product using appropriate techniques, with video evidence, and justify every implementation decision.

  • Fully functional — video evidence of all success criteria being met
  • Appropriate techniques — loops, data structures, libraries, justified
  • Evaluate & justify implementation choices and testing strategy

Criterion D: Moderator Mark Bands

Criterion D is worth 12 marks — the highest weighting in the IA. Moderators require video evidence that the product functions, and written justification for why specific techniques were used.

To Reach 1–3 / 12
  • ✔ Some working code
  • ✘ Product may not fully function
  • ✘ Techniques listed but not justified
  • ✘ Little or no testing evidence
  • ✘ Video evidence missing or incomplete
To Reach 4–6 / 12
  • ✔ Product mostly functional
  • ✔ Appropriate techniques used
  • ✔ Some justification of choices
  • ✘ But one area is weak — e.g. incomplete video, shallow justification, testing doesn't show response to issues
To Reach 7–9 / 12
  • ✔ Fully functional product with clear video evidence
  • ✔ Techniques are well-justified
  • ✔ Testing shows you responded to issues
  • ✘ Minor issues remain — e.g. one success criterion not fully demonstrated, or some testing lacks depth
To Reach 10–12 / 12
  • ✔ Fully functional, robust product
  • ✔ All success criteria demonstrably met in video
  • ✔ Implementation choices explicitly evaluated and justified
  • ✔ Thorough testing evidence showing iteration
  • ✔ Complex techniques used effectively
⚡ Ultimate Criterion D rule: The product must actually work — video evidence is mandatory. Techniques must be justified, not just listed. A technically impressive product with weak documentation still scores poorly.

E

📄 Criterion E Evaluation

4 marks · 400 words

Evaluate your product against each success criterion and justify future improvements in a way that is consistent with Criterion A.

  • Evaluate extent — did you meet each success criterion? Be specific.
  • Justify improvements — why these changes? What impact would they have?
  • Must be consistent with Criterion A

Criterion E: Moderator Mark Bands

Evaluation is not a summary of what you did. It is a criterion-by-criterion analysis of whether the final product met the success criteria, followed by justified improvements.

To Reach 2/4
  • ✔ Some evaluation of the product
  • ✔ Some improvements suggested
  • ✘ Evaluation may be vague or general
  • ✘ May not reference success criteria directly
  • ✘ Improvements may not be justified
To Reach 3/4
  • ✔ Clear evaluation against most success criteria
  • ✔ Improvements identified with some justification
  • ✔ Generally consistent with Criterion A
  • ✘ But one area is weak — e.g. some criteria not addressed, justification shallow, or limited evidence
To Reach 4/4
  • ✔ Criterion-by-criterion evaluation with specific evidence
  • ✔ Improvements clearly justified with expected impact
  • ✔ Fully consistent with Criterion A
  • ✔ Honest about limitations and what would be done differently
⚡ Ultimate Criterion E rule: A vague "it went well" evaluation scores low. Moderators look for criterion-by-criterion analysis with specific evidence. Improvements must be justified — not just a wish list. Consistency with Criterion A is checked explicitly.
