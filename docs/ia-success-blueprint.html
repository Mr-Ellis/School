Why You Must Use Classes and OOP From Day 1

This is not optional. The way you structure your code from the very first line determines whether you can demonstrate complexity in Criterion C — and complexity is where the marks are.

If you write everything inside one main.py file with 2,000 lines of code, you will:

  • Lose marks for decomposition and modularity
  • Struggle to explain your code line-by-line (the One Rule)
  • Have no clear class structure to discuss in Criterion C
  • Make debugging almost impossible

The fix is simple: Build your GUI with classes from Day 1. Your MainWindow is a class. Each screen is a class. Your database manager is a class. This is the pattern that demonstrates OOP naturally, without forcing artificial domain classes.

Your file structure should look like this from the start:

project/
├── main.py              # Starts the app
├── gui/
│   ├── main_window.py   # class MainWindow(ctk.CTk)
│   ├── dashboard.py     # class DashboardFrame(ctk.CTkFrame)
│   └── forms.py         # class AddRecordFrame(ctk.CTkFrame)
├── database/
│   └── database.py      # class DatabaseManager
└── models/
    └── record.py        # class Record

This structure alone demonstrates decomposition, modularity, and OOP — all valued in Criterion C.

The One Rule

If you cannot explain a block of code line-by-line, you should not submit it.

This applies to AI-generated code, copied code, and code from this framework.

Common Mistakes That Lose Marks

  • Putting everything in one main.py file (2,000+ lines)
  • No separation between GUI, logic, and database
  • Hardcoding values instead of using parameters
  • No validation — app crashes on empty input
  • No error handling — database errors crash the app
  • Submitting code you cannot explain

AI Usage Expectations

AI may be used as a learning tool, but:

  • You must understand all code you submit.
  • You must be able to explain how it works.
  • You must acknowledge AI assistance where required.
  • You must not submit code you cannot explain.

The rule: If you cannot explain it line-by-line, do not include it.

Criterion C Guidance

Criterion C is worth 12 marks — the biggest single criterion. It assesses the complexity and ingenuity of your solution, not just whether it works.

  • Focus on 1-3 complex techniques — not your whole program
  • Explain why, not just what — justify your design decisions
  • Annotate your code — screenshots with labels explaining each part
  • Reference your sources — tutorials, frameworks, Stack Overflow solutions you adapted
  • Show decomposition — classes, functions, modules, clear structure

Strong Criterion C answers: OOP with multiple classes, complex algorithms (sorting, searching, calculations), database relationships, input validation, error handling, and API integration.

Criterion D Guidance

Criterion D requires a video demonstration (2-7 minutes for HL, recommended for SL) showing your product meeting every success criterion.

  • Plan your video — don't improvise it after coding
  • Show every success criterion — narrate what you're demonstrating
  • Include test evidence — normal, boundary, and abnormal cases
  • Keep it clear — readable screens, clear narration
  • Show client feedback — what they tried, what broke, what changed
