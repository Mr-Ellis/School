Why classes and OOP matter from Day 1

The 2027 curriculum rewards technical ingenuity and complex code in Criterion D. If you write everything in one main.py file with 2,000 lines, you will:

  • Lose marks for decomposition and modularity
  • Struggle to explain your code (the One Rule)
  • Have no clear structure to discuss in your documentation
  • Make debugging almost impossible

The fix is simple. Build your GUI with classes from Day 1. Your MainWindow is a class. Each screen is a class. Your database manager is a class. This is the pattern that demonstrates OOP naturally.

project/
├── main.py              # Starts the app
├── gui/
│   ├── main_window.py   # class MainWindow(ctk.CTk)
│   ├── dashboard.py     # class DashboardFrame(ctk.CTkFrame)
│   └── forms.py         # class AddRecordFrame(ctk.CTkFrame)
├── database/
│   └── database.py      # class DatabaseManager
└── models/
    └── record.py        # class Record

Common mistakes that lose marks

  • Putting everything in one main.py file (2,000+ lines)
  • No separation between GUI, logic, and database
  • Hardcoding values instead of using parameters
  • No validation — app crashes on empty input
  • No error handling — database errors crash the app
  • Submitting code you cannot explain

Know your targets

Criterion C & D guidance

These are the two criteria where your project either shines or falls flat.

6 MARKS

Criterion C — System Overview

Assesses your system model, algorithms, and testing strategy.

  • System model: UML diagrams or flowcharts showing classes, database tables, and how they connect
  • Algorithms: Document the logic for your key features using pseudocode or flowcharts
  • Testing strategy: Describe how you will test each success criterion — normal, boundary, and abnormal cases

Examiners look for: a clear, complete system model, well-documented algorithms, and a testing plan that maps directly to your success criteria.

12 MARKS

Criterion D — Development

Assesses your fully functional product, technical ingenuity, and supporting video.

  • Video demonstration: Submit a video showing your product working and testing each success criterion
  • Technical ingenuity: Demonstrate complex techniques such as OOP, recursion, database relationships, and advanced algorithms
  • Testing evidence: Show normal, boundary, and abnormal test cases running in your video

Examiners look for: a working product that solves a complex problem, clean and well-commented code, and clear demonstration of testing.

Self-check

Checkpoint questions

You should be able to answer all of these at any point in the project:

  • What classes have you created and why?
  • What data is stored in your database?
  • How are your tables related?
  • What validation have you implemented?
  • Which success criteria are complete?
  • What testing have you carried out?
  • What would you improve with more time?
  • Can you explain every line of your code?
