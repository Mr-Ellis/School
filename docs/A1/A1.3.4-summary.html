A1.3.4 – Evaluate Polling & Interrupt Handling

📌 Learning Objective

  • Evaluate the use of polling and interrupt handling in different scenarios
  • Compare them across six criteria: event frequency, CPU overhead, power source, event predictability, controlled latency and security
  • Justify which method is best for a given real-world system

💡 The Big Idea — Two Strategies for Detecting Events

An operating system must detect when a device needs attention. There are two fundamental strategies:

Polling – the CPU repeatedly checks a status register or memory location to see whether something has happened.

Interrupt handling – the external device asserts a signal that asynchronously diverts the CPU to a service routine (ISR) when the event occurs.

Choosing between them is an engineering trade-off that centres on how often the event occurs, how tight the latency budget is, and how expensive each check or context switch will be.

📊 Comparison — The Six Evaluation Criteria

Click any card to reveal the full comparison for that criterion.

📈 Event Frequency Click to flip
Polling: Suits high-rate or continuous streams where an event is almost always ready (e.g. 100 Gbit/s packet capture).

Interrupts: Best for sparse or bursty events (e.g. key presses, USB hot-plug) so the CPU can sleep between arrivals.
⚙️ CPU Overhead Click to flip
Polling: Each poll executes a branch and possibly a bus transaction even when nothing happened — overhead scales with polling rate.

Interrupts: None while idle; a context switch and ISR prologue on each interrupt. Overhead is amortised.
🔋 Power Source Click to flip
Polling: Continuous polling prevents deep sleep states — undesirable on battery-powered devices.

Interrupts: Allows the core to remain in low-power C-states until the interrupt fires; advantageous for mobile and IoT.
🎯 Event Predictability Click to flip
Polling: Latency is deterministic — at most the time between successive polls. Good for hard real-time if the interval is short enough.

Interrupts: Latency depends on masking, priority and ISR length. Generally low, but subject to jitter.
⏱️ Controlled Latency Click to flip
Polling: Minimum latency = 0 (tight loop); maximum = polling interval. Good for hard real-time.

Interrupts: Usually low (≈ µs–tens of µs on desktops) but subject to jitter from other interrupts and critical sections.
🔒 Security Concerns Click to flip
Polling: No asynchronous control transfers, so fewer chances for interrupt vector hijacking or ISR stack smashing.

Interrupts: Adds a privileged entry point per vector; bugs in ISRs widen the attack surface (e.g. DMA attacks, spurious-interrupt DoS).

🌍 Real-World Scenarios

For each scenario, click the question to reveal which method dominates and why.

⌨️ Keyboard and mouse on a laptop
  • Winner: Interrupts — human input is infrequent; waking on each key saves battery.
  • Polling would require the CPU to continuously check the keyboard and mouse, wasting cycles and draining the battery.
  • Gaming keyboards may add optional high-rate polling (≈ 1 kHz) on mains-powered PCs for sub-millisecond latency.
🌐 High-speed network interfaces (10–400 GbE)
  • Winner: Hybrid — start with an interrupt, then switch to adaptive polling ("poll mode") while the ring buffer stays above a threshold.
  • This reduces interrupt storms under load while avoiding wasted cycles when idle.
  • Pure polling would waste CPU when traffic is low; pure interrupts would cause excessive context switching when traffic is high.
💾 NVMe SSD I/O
  • Winner: Interrupts for normal workloads; polling for tail-latency-critical datacentres.
  • Polling avoids the cost of interrupt delivery and context switches when thousands of I/O completions per core are pending.
  • For typical desktop use, interrupts are more efficient because I/O is sporadic.
🔌 Small embedded sensor node
  • Winner: Polling — a tight loop when the device has no MMU and runs a single control task at 100 Hz.
  • If energy is critical, designers often use timer interrupts to wake, poll quickly, then sleep again.
  • Pure polling is simple and predictable for this regular, low-rate task.
🤖 Hard real-time motor control (PLC, flight computer)
  • Winner: Polling or timer-driven cyclic executive for the control loop.
  • Asynchronous interrupts are disabled during the critical section to guarantee that no interrupt jitter violates control-law deadlines.
  • Predictability and controlled latency are more important than power efficiency here.

⚖️ When to Choose Which

Prefer polling when:

  • The event rate is high enough that most polls succeed (≈ > 50% hit ratio).
  • You need a strictly bounded latency shorter than the platform's worst-case interrupt latency.
  • The CPU would be awake anyway (server core already pinned to 100% utilisation).

Prefer interrupt handling when:

  • Events are sparse or bursty, so wasted polls would dominate.
  • Battery life or thermal headroom matters.
  • Security auditors require minimal privileged code paths in the main loop.

🔄 Putting It Together

Modern systems seldom commit exclusively to one style. Instead they blend both techniques, using interrupts to wake up a driver and then switching to short bursts of busy polling while a queue is non-empty. This adaptive approach balances power, throughput and latency across a wide dynamic range.
