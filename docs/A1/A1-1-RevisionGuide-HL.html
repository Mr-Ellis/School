1. Inside the CPU

What the CPU is

The CPU executes program instructions. It contains the Control Unit (which coordinates everything), the Arithmetic Logic Unit (which does maths and logic), and a small number of very fast storage locations called registers. Registers are not the same as RAM — they sit inside the CPU, hold one value each, and are accessed in a single clock cycle.

The registers you need to know

RegisterHoldsIts job in the cycle
Program Counter (PC)The address of the next instruction to fetchIncremented after each fetch, so the next cycle looks at the following instruction
Memory Address Register (MAR)The address currently being read from or written toSends that address onto the address bus
Memory Data Register (MDR)Data in transit between the CPU and memoryBuffers the data arriving from or leaving for RAM
Instruction Register (IR)The instruction currently being decoded or executedFeeds the Control Unit with what needs to happen next
Accumulator (ACC)Intermediate results of ALU operationsWritten back to a register or memory at the end of execute
The MAR/PC distinction: the PC holds the address of the next instruction. The MAR holds the address that is currently on the bus. In fetch, the PC is copied into the MAR — for one moment they hold the same value — then the PC is incremented and the two diverge.
The IR/MDR distinction: the IR holds an instruction (a command). The MDR holds data — the thing being operated on, or the instruction while it is in transit along the bus. The MDR is a temporary buffer; the IR is where the instruction lives while the Control Unit decodes it.

The three buses

Buses are the wires that carry signals between the CPU, memory and I/O devices.

BusDirectionCarries
Address busOne-way, CPU → memoryThe address of the location being accessed
Data busTwo-wayThe actual data or instruction
Control busTwo-waySignals such as read/write, clock, interrupts

The fetch–decode–execute cycle

FETCH 1. The address in the PC is copied into the MAR. 2. The MAR places that address on the address bus. 3. The Control Unit sends a read signal on the control bus. 4. Memory returns the instruction on the data bus into the MDR. 5. The MDR's contents are copied into the IR. 6. The PC is incremented, ready for the next cycle. DECODE 7. The Control Unit examines the instruction in the IR. 8. It identifies the operation (the opcode) and any operands. 9. It activates the components that will be needed for execution. EXECUTE 10. The ALU or another unit performs the operation. 11. The result is written back to a register or to memory.
Common mistake: saying the MDR "decodes" the instruction. Decoding is done by the Control Unit, reading from the IR. The MDR's only job is to hold data in transit.

2. Primary memory

RAM vs ROM

RAMROM
VolatilityVolatile — contents are lost when power is removedNon-volatile — contents survive without power
Read/writeBoth readable and writableRead-only in normal operation
Typical useHolding programs and data that are currently in useHolding firmware — startup instructions the machine needs before anything is loaded
Why firmware lives in ROM: startup instructions must be available the moment the machine is switched on — before RAM has been populated, before any disk has been read. RAM can't do that job because it loses its contents when the power is off. ROM is non-volatile, so its contents are there instantly at power-on, and read-only, so software can't accidentally corrupt it.

Cache

Cache is small, very fast memory between the CPU and RAM. It holds copies of recently used instructions and data.

  • Cache hit — the CPU finds what it needs in cache. It proceeds almost immediately.
  • Cache miss — the CPU doesn't find what it needs. It fetches from RAM, which takes many times longer, and the CPU stalls while it waits.

A higher hit rate means fewer slow RAM fetches. The CPU spends less time waiting and more time executing.

Mental model: cache is the small pile of books on your desk. RAM is the bookshelf across the room. A hit means the book you want is already on the desk.

3. Specialist processors — the GPU

Why a GPU is different from a CPU

A CPU has a small number of powerful cores (typically 4–16). Each core has complex logic to handle branching, prediction and varied work. A GPU has hundreds or thousands of much simpler cores. Each core is weak on its own, but the sheer number of them means the GPU can do vast numbers of small calculations at the same time. The GPU also has its own high-bandwidth memory to feed those cores.

CPUGPU
CoresFew (4–16)Many (hundreds–thousands)
Per-core complexityHigh — branching, prediction, cachingLow — simple arithmetic, no branching
Best atVaried, sequential workRepetitive, parallel work

Why GPUs suit parallel workloads

Any task made up of many independent calculations — ones where the result of one doesn't affect the next — can run in parallel. Rendering, matrix multiplication and image processing all fit this pattern.

Worked example — image filtering. Applying a blur to a 12-megapixel photo: each pixel's new value depends only on the pixels immediately around it, not on what happens to any other pixel. So each pixel can be processed independently. On a CPU, 12 million pixels have to be processed in batches across 8 cores. On a GPU, thousands of cores work through them simultaneously, and the filter completes in a fraction of the time.
Why the simplicity is an advantage: because GPU cores don't need to branch or predict, they use far fewer transistors each. That's how thousands of them fit on a single chip. Simplicity isn't a weakness — it's what makes the parallelism possible.

How CPU and GPU work together

  • The CPU manages the overall process, prepares the data, and handles anything sequential or conditional.
  • The CPU hands the parallel chunks over to the GPU.
  • Data travels between them over a high-speed bus (typically PCIe). Transfers are slow compared to compute, so data is batched into large chunks.
  • The CPU synchronises — it waits for the GPU to finish a batch before doing any step that depends on the result.

5. Compression

The two families

LosslessLossy
Original recoverable?Yes — exactlyNo — data is permanently discarded
What happensRedundancy is encoded more efficientlySome information is thrown away based on what the human senses won't miss
Typical examplesPNG, ZIP, FLACJPEG, MP3, most video codecs
Used forText, code, archives, anything that must be exactPhotos, audio, video — where approximate is acceptable

Run-length encoding (RLE)

RLE replaces each run of identical characters with a count followed by the character. It's lossless and simple, and works well on data with long repeats.

Worked example. Take the string AAABBBBBBBCCD:
  • Runs: AAA, BBBBBBB, CC, D
  • Encoded: 3A7B2C1D
  • Original: 13 characters. Encoded: 8 characters. Saving: 5 characters.
RLE is shorter here but not always. If a string has no repeats — ABCDEF — RLE makes it longer. It only helps when runs are common.

Transform coding (MP3, JPEG)

  1. The raw signal is converted from time-domain samples into frequency components using a transform (MP3 uses MDCT).
  2. The encoder identifies components the listener cannot perceive: very quiet sounds, and sounds masked by louder nearby frequencies.
  3. Those components are permanently discarded. This is why the method is lossy.
  4. The remaining data is encoded compactly, producing a much smaller file.
Why this works: human hearing has limits. Frequencies above ~20 kHz are inaudible to most adults, and quiet sounds next to loud ones at similar frequencies are completely masked. Discarding those components costs nothing perceptible but saves enormous space.

6. Cloud computing

ModelProvider managesCustomer managesTypical use
SaaS — Software as a ServiceEverything — hardware, OS, applicationJust uses the softwareEmail, office apps, CRM systems
PaaS — Platform as a ServiceHardware, OS, runtime, middlewareThe application code and its configurationDeploying a custom web app
IaaS — Infrastructure as a ServicePhysical hardware onlyOS, runtime, apps, security, scalingRunning a bespoke server environment
Pizza analogy: SaaS is eating out — someone else does everything. PaaS is a ready-made pizza base — you add your own toppings. IaaS is buying the ingredients — the kitchen and the cooking are on you.

Trading off the models

  • SaaS is fast to adopt but you get whatever features the vendor offers.
  • PaaS lets you build custom software without managing servers.
  • IaaS gives full control but you also carry the operational burden: patching, security, capacity planning.

The further down the stack you go (SaaS → PaaS → IaaS), the more control you get and the more responsibility you take on. Choose the highest level that still meets your requirements.

7. Operating systems

What an operating system does

The OS sits between the user, the application software and the hardware. Its main jobs: managing processes (deciding which runs when), managing memory (deciding what lives where), managing I/O (talking to devices), managing files, and providing security.

Processor scheduling

Only one process can run on a core at a time. Two common scheduling algorithms:

First-Come First-Served (FCFS)Round Robin (RR)
RuleWhoever arrives first runs until they finishEach process runs for a fixed time slice, then goes to the back of the queue
FairnessPoor — a long process can block everyone behind itBetter — short processes get a slice quickly, so response times are shared
OverheadLow — few context switchesHigher — a context switch each time a time slice expires
Best forBatch work where jobs are similar lengthInteractive systems where responsiveness matters
Convoy effect: under FCFS, if a long process arrives first, all the short processes behind it have to wait until it finishes. Like a slow lorry on a single-lane road.

Polling vs interrupts

  • Polling: the CPU checks the device regularly, at fixed intervals. Simple and predictable, but wastes cycles when the device has nothing to report.
  • Interrupts: the device signals the CPU when it needs attention. The CPU can be doing other work or sleeping until the signal arrives.
Where each wins: polling suits devices that are busy almost all the time — the overhead of checking is small compared to the throughput. Interrupts suit infrequent, unpredictable events — the CPU isn't tied up checking for something that hasn't happened.

Memory management and paging

The OS divides memory into fixed-size pages (logical blocks of a program) and frames (physical blocks of RAM). Pages load into any free frame, so a program doesn't need to occupy one contiguous chunk of memory.

Benefits:

  • Reduces external fragmentation — free memory that's unusable because it's split into small gaps.
  • Enables virtual memory — pages not currently in use can be written to disk, so programs larger than physical RAM can still run.
  • Simplifies allocation — any free frame will do.

Deadlock

Deadlock happens when processes each hold a resource and each wait for a resource another process holds. None can proceed.

Process A holds resource R1 and requests R2. Process B holds resource R2 and requests R1. Neither releases what it holds until it gets what it wants. → Circular wait. Neither can proceed. Deadlock.

For deadlock to occur, four conditions must all hold at once:

  • Mutual exclusion — resources can't be shared; one process at a time.
  • Hold and wait — a process holds one resource while waiting for another.
  • No preemption — resources can't be forcibly taken back.
  • Circular wait — a cycle of processes each waiting on the next.

Preventing deadlock means breaking one of these conditions — for example, imposing a global order on resources so a circular wait can never form.

8. Pipelining and instruction-level parallelism (HL only)

The idea

Executing an instruction takes several steps — fetch it, decode it, execute it, write the result back. In a non-pipelined processor each step waits for the previous one to finish, and the hardware sits idle most of the time.

Pipelining breaks execution into stages and lets different stages of different instructions run at the same time. Each stage handles one instruction per clock cycle, like stations on an assembly line.

Clock: 1 2 3 4 5 6 Instr 1: F D E W Instr 2: F D E W Instr 3: F D E W Instr 4: F D E W ↑ one instruction completes per clock cycle in the steady state

Where F = fetch, D = decode, E = execute, W = write-back.

Speed-up: without pipelining, one instruction completes every four cycles. With a 4-stage pipeline, once it is full, one instruction completes every cycle. Up to 4× throughput for the same clock speed.

The pipeline stages

StageWhat happens
FetchLoad the next instruction from memory into the IR
DecodeControl Unit interprets the instruction — identifies the operation and its operands
ExecuteThe ALU or other unit carries out the operation
Write-backThe result is written to a register or memory

Pipelining in a multi-core processor

Every core has its own pipeline, ALU and registers. All cores overlap stages simultaneously and work independently on tasks assigned by the OS. The combination multiplies the number of instructions completed per unit time.

Branches — the pipeline's enemy

A branch (if, while, function call) means the next instruction to fetch depends on the result of the current one. While the branch is being evaluated, the pipeline may already have fetched instructions that turn out to be wrong. Those must be flushed — discarded, wasting the work done on them.

Common ways to reduce the branch penalty:

  • Branch prediction — the CPU guesses which way the branch will go and fetches down that path. If the guess is right, no stall. If wrong, the mispredicted instructions are flushed.
  • Speculative execution — execute both possible paths in parallel, keep whichever turns out to be correct, discard the other.
  • Delayed branch — the compiler places a useful instruction in the "branch delay slot" so it runs regardless of which way the branch goes.
More stages ≠ always better. Adding pipeline stages adds overhead (registers/latches between stages cost time), increases the branch misprediction penalty, and not every instruction uses every stage. Beyond a point, throughput gains flatten.

9. Compilers and interpreters (HL only)

What they do

High-level code (Python, Java, C) has to be turned into something the CPU can actually execute. There are two approaches:

CompilerInterpreter
When it translatesWhole program, before executionOne statement at a time, during execution
OutputAn optimised machine-code fileNo file — direct execution
Speed of executionFaster — native code, optimisedSlower — translation overhead at run time, repeated in loops
Error reportingAll errors at once, after translation completesAt the exact statement reached when the error occurs
Best forFinal deployment where speed mattersDevelopment and testing — fast iteration
Why compiled code is faster: the compiler translates the whole program into optimised machine code before it runs. At run time the CPU executes native instructions directly. An interpreter, by contrast, has to translate each statement as it runs, and that translation work is repeated every time a loop goes round.
Why interpreters are better for development: there is no build step, so a change can be tested immediately. Errors surface at the exact line reached, which makes bugs easier to locate. The trade-off is that execution is slower — fine for testing, not for a deployed product where speed matters.

10. Exam technique

Command terms

TermWhat the examiner wants
State / Give / NameOne short answer. No explanation.
OutlineBrief summary. Main points only.
DescribeSay what happens or what it is — no need to explain why.
ExplainSay how or why. Every mark needs a distinct reason or mechanism.
CompareBoth similarities and differences.
EvaluateAdvantages, disadvantages, and a justified conclusion. Without the conclusion, you can't score the final mark.

Marks → points

  • 2 marks = two distinct points, or one point developed with a reason.
  • 3 marks = three distinct points, or one point developed in three stages.
  • 4 marks = usually four distinct points, or two points each developed with a reason.
  • 6 marks = typically three developed arguments plus a judgement.
The most common cause of lost marks is writing one vague sentence for a multi-mark question. If a question is worth 4 marks, you need at least four distinct pieces of information.

How to write an "explain" answer

Use a two-part structure: what happens + why / how it leads to the effect.

  • Weak: "Pipelining makes the CPU faster."
  • Strong: "Pipelining lets different stages of consecutive instructions overlap, so once the pipeline is full a core can complete one instruction per clock cycle instead of one every four — the processor finishes more instructions per second at the same clock speed."

11. Practice questions

Try each one without looking back at the notes. Write your answer first, then open the model to compare.

Q1. A processor has a four-stage pipeline. Explain what happens during the decode and write-back stages, and why pipelining increases instruction throughput. (4 marks) — Show a model answer ▼

In the decode stage the Control Unit reads the instruction in the IR and works out which operation is required and what operands it needs, so the correct components can be prepared for execute. In the write-back stage the result of the operation is stored, either in a register or in memory. Pipelining increases throughput because different stages of different instructions run at the same time — while one instruction is being decoded, the next is being fetched, and the one before that is being executed. Once the pipeline is full, a core can complete one instruction per clock cycle instead of one every four cycles.

Q2. Explain why a branch instruction can reduce the benefit of pipelining, and describe one technique a processor can use to reduce this problem. (4 marks) — Show a model answer ▼

A branch means the next instruction to fetch depends on the result of the current one. While the branch is being evaluated, the pipeline may already have fetched and started decoding instructions from the wrong path. When the branch is resolved, those instructions must be discarded — a pipeline flush — wasting the cycles that were spent on them. To reduce this, the processor can use branch prediction: it guesses which way the branch is likely to go and fetches down that path. If the prediction is correct the pipeline never stalls; only a misprediction causes a flush, and modern predictors are accurate enough that most branches do not cost anything.

Q3. Explain why increasing the number of pipeline stages does not always improve performance. (2 marks) — Show a model answer ▼

Each additional stage adds overhead: registers or latches between stages take time to propagate, and the clock cannot run faster than the slowest stage allows. Deeper pipelines also increase the branch misprediction penalty, because more wrong-path instructions have to be flushed. Beyond a certain point, these costs outweigh the extra overlap, and throughput stops improving.

Q4. Explain why compiled code generally executes faster than interpreted code, and give one situation where an interpreter is the better choice. (4 marks) — Show a model answer ▼

A compiler translates the whole program into optimised machine code before it runs, so at run time the CPU executes native instructions directly with no translation overhead. An interpreter translates each statement as it runs, and repeats that translation work every time the program passes through the same code — for example, inside a loop. Because of this repeated overhead, interpreted execution is slower. An interpreter is the better choice during development: there is no build step, so a change can be tested immediately, and errors surface at the exact statement that caused them, making bugs easier to locate.

Q5. A developer is writing a program to filter live video from a webcam. Explain how the CPU and GPU would divide the work, and why this division suits their architectures. (5 marks) — Show a model answer ▼

The CPU would handle the sequential, varied parts of the pipeline — reading frames from the webcam, managing the user interface, and deciding what to do with the output. Applying the filter to each frame is a parallel task: the same calculation is applied to every pixel, and each pixel's result does not depend on the others. The CPU hands that pixel-level work to the GPU. The GPU's thousands of simple cores can process many pixels simultaneously, which is far faster than a CPU's handful of cores working through them in sequence. Because the transfer of data over PCIe is slow compared to compute, the CPU batches frames into large chunks before sending them. When the GPU finishes a batch, the CPU synchronises — it waits before displaying the result or encoding it — because those steps depend on the filtered output.

Q6. A server application uses round robin scheduling. Explain one advantage and one disadvantage compared to first-come first-served in this context. (4 marks) — Show a model answer ▼

Under round robin each process runs for a fixed time slice and is then moved to the back of the queue. The advantage is fairness: a long-running process cannot monopolise the processor, so short requests from other users get served quickly. Under FCFS a long job would block everyone behind it (the convoy effect), which would make the server feel unresponsive. The disadvantage is overhead: every time a time slice expires the operating system must perform a context switch, saving the current process's state and loading another. On a busy server these switches happen frequently, and the CPU time spent on them is time not spent on useful work.

Q7. Explain what deadlock is, describe the four conditions that must all hold for it to occur, and suggest one way a system can prevent it. (5 marks) — Show a model answer ▼

Deadlock is a state in which two or more processes are each waiting for a resource that another process holds, so none can proceed. Four conditions must all hold at once. Mutual exclusion: each resource can only be held by one process at a time. Hold and wait: a process is holding at least one resource while requesting another. No preemption: a resource cannot be forcibly taken away from a process that holds it. Circular wait: a cycle of processes each waiting on a resource held by the next in the cycle. To prevent deadlock, the system could break the circular wait by imposing a global order on all resources — every process must request resources in the same predefined order. With that rule in place, no cycle can form and deadlock becomes impossible.

Q8. A user complains that their laptop battery drains quickly and that the mouse pointer sometimes lags. The system uses polling to read both the mouse and the keyboard. Explain what is wrong and how interrupts would improve things. (4 marks) — Show a model answer ▼

Polling means the CPU checks the mouse and keyboard at fixed intervals even when nothing has changed. For most of the time no key is pressed and no mouse movement has occurred, so the CPU is running checks that return nothing and cannot drop into a low-power state. This wastes cycles and drains the battery. Interrupts would fix this: the mouse and keyboard would only signal the CPU when there was new input, so between events the CPU could sleep or do other work. Response latency would also improve, because an interrupt is handled immediately rather than waiting for the next poll — the pointer would feel responsive instead of lagging.
