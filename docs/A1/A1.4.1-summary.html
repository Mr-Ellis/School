A1.4.1 – Interpreters and Compilers (HL)

📌 Learning Objective

  • Describe how compilers, interpreters and JIT compilers turn source code into something the computer can run
  • Compare them on error detection, speed, portability and memory use
  • Choose the right translation method for a given situation

💡 The Big Idea

A computer only understands machine code — simple instructions made of 1s and 0s. When you write code in a language like Python, Java or C++, something has to translate it into machine code. There are three main ways to do this:

1. Compiler – translates the whole program into machine code before it runs.

2. Interpreter – reads the code and runs it line by line, translating as it goes.

3. JIT compiler – a mix of both. Starts interpreting, then compiles the hot parts (the bits that run most often) into machine code while the program is running.

🔧 How Each Method Works

Click any card to reveal what that method does.

🏗️ Compiler Click to flip
What it does: Reads the whole program and turns it into machine code before the program starts.
Errors: Found before you run it — the compiler checks everything first.
Speed: Very fast at run time (the translation is already done).
Examples: C, C++, Rust, Go.
📜 Interpreter Click to flip
What it does: Reads the code line by line and runs each line straight away.
Errors: Found while the program runs — you only see them when that line is reached.
Speed: Slower at run time (translation happens every time).
Examples: Python, Ruby, JavaScript (in the browser).
⚡ JIT Compiler Click to flip
What it does: Starts by interpreting, then spots the parts of code that run the most and compiles those into machine code on the fly.
Errors: Found early for syntax; some checks happen at run time.
Speed: Nearly as fast as a compiler after a short warm-up.
Examples: Java, C# (.NET), modern JavaScript (V8).
📦 Bytecode Click to flip
What it is: A middle step between source code and machine code. Simpler than source, but not tied to one type of computer.
Why it helps: You can write it once and run it anywhere — you just need a small program (a virtual machine) to read it.
Examples: Python .pyc files, Java .class files, WebAssembly.
🔤 Lexer & Parser Click to flip
Lexer: Breaks your source code into small pieces called tokens (keywords, names, symbols).
Parser: Arranges those tokens into a tree that shows the structure of the program.
Why it matters: Both compilers and interpreters use these first steps — the difference is what happens next.
🧠 Virtual Machine Click to flip
What it is: A program that acts like a pretend computer. It reads bytecode and runs it.
Why it helps: The same bytecode can run on Windows, Mac or Linux — you just need the right VM for each one.
Examples: Java Virtual Machine (JVM), Python's interpreter, the .NET runtime.

📊 Comparing the Methods

This table is the heart of A1.4.1 — learn to compare the methods across these criteria.

Criterion Compiler Interpreter JIT Compiler
When are errors found? Before the program runs — the compiler checks everything first. While the program runs — you only find errors when that line is reached. Syntax errors found early; some issues only show up during execution.
How long until it starts? Slow to compile (can take minutes), but instant once done. Almost instant — no compile step at all. Fast to start, but slows down briefly as it "warms up".
How fast does it run? Fastest — the translation is already done. Slowest — translates every line every time. Almost as fast as a compiler once warmed up.
Portability Poor — must be recompiled for each type of computer. Excellent — the same source code runs anywhere with the right interpreter. Good — bytecode runs anywhere with a VM, though the JIT must generate machine code per platform.
Memory use Moderate. Small. Largest — it needs the interpreter, bytecode, and generated machine code all at once.
Best for… Games, operating systems, anything that must run as fast as possible. Learning, scripting, quick tests — where instant feedback matters. Long-running, portable apps like web browsers and servers.

🌍 Which Method Fits? — Scenarios

For each scenario, click the question to reveal the best method and why.

🐍 Writing a quick script to test an idea
  • Winner: Interpreter (e.g. Python).
  • No compile step — you type a line, hit run, and see the result instantly.
  • Perfect for experimenting, notebooks and small scripts.
  • Slower at run time, but that doesn't matter if you're only running it once.
🎮 A video game physics engine
  • Winner: Compiler (C++ or Rust).
  • Every frame needs to run in a few milliseconds — speed is everything.
  • Compiled code runs directly on the processor with no translation overhead.
  • Not portable — you'd need a separate build for Windows, Mac and consoles.
📱 A mobile app that must run on Android and iOS
  • Winner: Bytecode + JIT.
  • Compile once to bytecode; each phone's virtual machine runs it.
  • The JIT speeds up the parts of the app you use most.
  • Best mix of portability and speed for mobile apps.
🌐 Running JavaScript in a web browser
  • Winner: JIT compiler.
  • The browser needs to start quickly (so users aren't kept waiting), but also run fast once a page is loaded.
  • JIT gives quick startup AND good speed after a brief warm-up.
  • If a JIT optimises something and later finds it was wrong, it can go back to interpreting — so the code stays correct.
🔒 A macro inside a spreadsheet file
  • Winner: Bytecode interpreter (in a sandbox).
  • Macros come from unknown sources — they need to be checked before they run.
  • The sandbox limits what the macro can do (no deleting your files, no calling home).
  • Speed isn't critical — safety is.
