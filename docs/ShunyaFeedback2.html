What is preventing 8–9+

The primary issue is testing effectiveness. A likely moderator comment would be:

“Appropriate techniques have been used and the product appears functional. Implementation choices are partially evaluated. However, testing effectiveness is largely described rather than justified, and evidence for extreme testing is limited.”

If extreme testing evidence is added, testing effectiveness is justified with actual results, and every success criterion is demonstrated in a video, the submission has a realistic pathway into the 8–9+ band.

! The biggest mistakes you could make

Thinking that lots of testing tables automatically score highly

The document contains many tables. Moderators do not reward the number of test cases — they reward evidence that testing demonstrates functionality and reliability. A table showing an input and an output does not automatically justify the testing strategy.

Example: a table showing input 10 → output 1 proves that one calculation works on one input. It does not prove the algorithm is reliable, nor that the testing strategy is effective.

Treating explanation as evaluation

Many sections follow the pattern “I used pandas because…”, “I used JSON because…”, “I used QTimer because…”. That is explanation. Evaluation requires an alternative, a limitation, a trade-off and a justification. Only some sections do this well.

Assuming invalid tests = complete testing

The write-up focuses heavily on invalid inputs. The moderator will still ask: where are the extreme tests? Where are the large datasets? Where are the performance tests? Where is evidence the application remains reliable over time?

1

Weighted stress scoring algorithm

This is your strongest computational technique. The algorithm applies weights to questionnaire answers, normalises the values, calculates a final stress score out of 10, and prevents negative overflow. It is a genuine multi-step calculation rather than a lookup.

You already evaluate it well on simplicity, interpretability and reduced precision. Make sure that evaluation is visible in the final write-up — the trade-off between a simple, explainable formula and a more precise but opaque one is exactly what moderators reward.

This is the algorithm most likely to be remembered, so it should lead the techniques section and appear early in the video.
2

Trend detection algorithm

Probably the most sophisticated element in the project. It loads historical data, creates a pandas dataframe, groups scores by hour, finds peak stress periods and generates recommendations from them. That is a real data-processing pipeline, not a single function.

This should be emphasised more during demonstrations. Show the prepared history data, show the grouped output, and show the recommendation that follows from it.

It is the clearest example of the project doing something a simple data-entry application cannot do.
3

Input validation

Multiple validation stages exist: missing values, invalid ranges, invalid data types and yes/no validation. This provides a strong source of abnormal testing, which is currently one of the better-evidenced areas.

In the write-up, make the sequence of checks explicit and show what happens when each one fails, rather than listing them as features.

Validation is easy to under-explain. Show the order of checks and the failure behaviour for each one.
4

Break recommendation system

The transformation from stress score to break duration is computational and should be treated as an algorithm in its own right. It maps a continuous score onto a discrete set of actions.

Show different stress levels producing different break durations in the video — that is a quick, clear demonstration of the mapping working across the full range.

Treating this as an algorithm rather than a UI feature raises the computational quality of the write-up.

2 Structure for each technique

Use this structure for every technique. Points F, H and I are the evaluation and justification points — those are what push a report from 7 into the 8–9+ band. The examples below use the weighted stress scoring algorithm.

A

What is the technique?

Explain the technique in one or two sentences, independent of your project.

“Weighted scoring is an algorithm that combines multiple inputs, each with its own importance, into a single normalised score.”
B

How is it used in my solution?

Connect the technique directly to your project.

“Each questionnaire answer is multiplied by its configured weight, the weighted values are summed and normalised, and the result is presented as a stress score out of 10.”
C

Why did I choose it?

Give the computational reason, not just the user-facing benefit.

“A weighted sum keeps the calculation interpretable: each question's contribution can be explained to the user, unlike a machine-learning model.”
D

What alternative could I have used?

Name a realistic alternative and say what is wrong with it.

“A trained machine-learning model could predict stress more accurately, but it would require labelled data the project does not have, and its decisions would be opaque to the user.”
E

What is a limitation?

Every technique has one. Naming it honestly strengthens the evaluation.

“The weighting scheme is fixed at design time, so it cannot adapt to an individual user's stress patterns.”
F

Why is my choice still appropriate? (evaluation)

Weigh the limitation against the benefit and reach a judgement.

“Although the weighting is fixed, it makes the score predictable and explainable, which matters more for a self-monitoring tool than marginal accuracy gains.”
G

How did I test it?

Describe the normal, abnormal and extreme cases you actually ran.

“I tested minimum scores, maximum scores, mixed weighted answers, and a continuous run of 10/10 responses to check the score did not overflow.”
H

Why was the testing effective? (justification)

Explain what the tests prove — not just that they were run.

“The extreme tests proved the normalisation holds at both boundaries, and the mixed tests proved each weight affects the final score as expected.”
I

What does the testing NOT prove? (evaluation of testing)

Name what remains unproven. This is the point most students skip.

“The tests confirm the algorithm behaves correctly on the cases I tried, but not that the score correlates with real physiological stress.”

E Evaluation checklist

The implementation sections already explain well. Use this to confirm nothing has slipped, especially for the testing discussion.

  1. I discussed at least one alternative for each major technique.
  2. I discussed the advantages of my chosen approach.
  3. I discussed the limitations of my chosen approach.
  4. I explained why the advantages outweigh the limitations.
  5. I explained what the testing demonstrates.
  6. I explained what the testing does not prove.
The quick evaluation test: if a paragraph can be rewritten as “I used X because it does Y”, it is probably explanation. If it includes an advantage, a limitation, an alternative and a trade-off, it is probably evaluation.
