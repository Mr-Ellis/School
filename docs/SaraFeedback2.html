JSON persistence missing — add this

The application stores all courses, assessment records, target grades and customised boundaries in ib_tracker_data.json. The load_data() and save_data() functions read and write the file, so data survives between sessions.

The section should discuss: why JSON was chosen over a relational database like SQLite (single local user, human-readable, no server, fits Python dictionaries); the advantage (simplicity, portability, hundreds of records fit comfortably); the limitation (the entire file is rewritten on every change, no schema enforcement, corrupted files could introduce invalid structures); and why the limitation is acceptable (six subjects, small numbers of assessments, so storage is effectively instantaneous).

JSON persistence is a real architectural decision, and the trade-off against a database is exactly what moderators reward.
5

Subject-selection validation missing — add this

The application requires exactly six IB subjects. The choose_subjects() function separates the input into a list and checks three conditions: exactly six subjects, every subject in the approved list, and no duplicates.

The section should discuss: what the three checks are; why they are needed (five subjects, seven subjects or duplicates would break every downstream calculation); an alternative (unrestricted text entry — more flexible but prone to spelling mistakes and inconsistent names); the advantage (invalid configurations are caught before data is saved); the limitation (students can only choose from the predefined list, so an unusual course would require a code change); and why the limitation is acceptable (the list covers the standard IB programme the tool is designed for).

This is stronger than the current score-validation section because it combines count, range and duplicate checking.
6

Average calculation missing — add this

The calculate_average() function sums all assessment percentages and divides by the number of assessments, returning None if no records exist to avoid division by zero.

The section should discuss: why a direct arithmetic mean was chosen over storing running totals (the number of assessments is small, and recalculating dynamically means edits and deletions are reflected immediately); the advantage (accuracy and simplicity); the limitation (real IB assessments often have different weightings, but the current implementation assumes equal weighting); and why the limitation is acceptable (the average is a quick estimate and feeds the target-grade prediction, not a formal grade calculation).

Average calculation underpins the prediction and recommendation systems, so it deserves its own section even though the maths is simple.

2 Structure for each new technique

Use this structure for the three new sections. Points F, H and I are the evaluation and justification points. The example below uses JSON persistence.

A

What is the technique?

Explain it in one or two sentences, independent of your project.

“JSON persistence stores application data as a human-readable text file that is loaded into memory at startup and written back to disk when data changes.”
B

How is it used in my solution?

Connect it directly to the project.

“load_data() and save_data() read and write ib_tracker_data.json, storing courses, assessments, target grades and customised boundaries.”
C

Why did I choose it?

Give the computational reason, not just the user benefit.

“The application is for a single student running locally, so a full database server would add complexity with no benefit.”
D

What alternative could I have used?

Name a realistic alternative and say what is wrong with it.

“SQLite would support indexed updates and schema validation, but it would require more setup for a dataset this small.”
E

What is a limitation?

Every technique has one.

“The entire file is rewritten on every save, and JSON does not enforce a schema, so a corrupted file could introduce invalid structures.”
F

Why is my choice still appropriate? (evaluation)

Weigh the limitation against the benefit and reach a judgement.

“Although rewriting the whole file would be inefficient at scale, six subjects and a small number of assessments make storage operations effectively instantaneous.”
G

How did I test it?

Describe the normal, abnormal, boundary and extreme cases you ran.

“I tested saving and reloading, restarting the program, a missing file, a corrupted file, and a 100-assessment dataset.”
H

Why was the testing effective? (justification)

Explain what the tests prove.

“The restart test proved persistence across sessions; the corrupted-file test proved the program fails safely rather than crashing; the large-dataset test confirmed storage remains fast enough for realistic use.”
I

What does the testing NOT prove? (evaluation of testing)

Name what remains unproven.

“The tests confirm the storage works at the sizes I tried, but not that JSON would remain efficient with thousands of assessments.”

E Evaluation checklist

Your grade mapping section already does this well. Use the checklist to confirm the three new sections match it.

  1. I discussed at least one alternative for each major technique.
  2. I discussed the advantages of my chosen approach.
  3. I discussed the limitations of my chosen approach.
  4. I explained why the advantages outweigh the limitations.
  5. I explained what the testing demonstrates.
  6. I explained what the testing does not prove.
The quick evaluation test: if a paragraph can be rewritten as “I used X because it does Y”, it is probably explanation. If it includes an advantage, a limitation, an alternative and a trade-off, it is probably evaluation.

3 Testing evidence · the biggest gap

The current draft contains very little testing analysis. This is the biggest mark risk. Run each test below, record the actual result, and tick it once you have evidence. The 25 tests cover normal, boundary, abnormal and extreme cases.

Normal, boundary, abnormal and extreme testing are four different things. Normal tests show the program works when used correctly. Boundary tests check the decision thresholds. Abnormal tests confirm invalid input is rejected safely. Extreme testing is separate: it confirms that valid input at the edge of the program's limits — large datasets, long inputs and repeated runs — is still handled correctly. A report with only normal and abnormal tests has not shown that the program holds up under load.
