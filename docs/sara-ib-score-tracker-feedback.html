🔧 Critical Fixes Needed

SC5 — Add Timing Evidence

What's wrong now: SC5 says "All calculation speed should be under 1s". Every function you have (calculate_average, calculate_grade, calculate_required_score) runs in microseconds, but there is no code that measures or displays this. In a video demo, you can't claim SC5 is met without showing a timer.

Why it matters: Criterion D explicitly requires evidence of testing. Timing claims need a printed value, not an assertion.

What to add: Wrap calculations in a timer and display the result:

import time

def timed(label, fn, *args, **kwargs):
    start = time.perf_counter()
    result = fn(*args, **kwargs)
    elapsed = (time.perf_counter() - start) * 1000  # milliseconds
    print(c(f"  [{label}: {elapsed:.2f} ms]", DIM_C))
    return result

# Usage in add_assessment, view_course_details, etc:
average = timed("avg", calculate_average, course["assessments"])
grade = timed("grade", calculate_grade, average, course["boundaries"])

How to test it: Run the app, add an assessment, and watch the console print timing values. They will be well under 1 ms — every time.

input_target_grade() Is Defined but Rarely Used

What's wrong now: input_target_grade() is a helper function, but setup_courses() and edit_course_settings() both call input_int("Target grade (1-7): ", min_val=1, max_val=7) directly instead of using the helper.

Why it matters: Having an unused helper is a small code-quality issue — but more importantly, if you later change the valid range (say, to include "no target"), you'd have to update two places instead of one.

What to add: Use the helper consistently:

# In setup_courses()
target = input_target_grade()  # instead of input_int(..., min_val=1, max_val=7)

# In edit_course_settings() 
course["target_grade"] = input_target_grade()

How to test it: Enter setup and confirm target grade validation still works for 0, 8, and "abc".

Design — Grade Boundaries Use String Keys

What's wrong now: DEFAULT_BOUNDARIES is defined with string keys:

DEFAULT_BOUNDARIES = {"7": 90, "6": 80, "5": 70, ...}

This is because JSON only supports string keys. That's a legitimate reason — but it means every lookup has to convert str(grade):

boundaries[str(target_grade)]

Why it matters: It's easy to forget and use boundaries[7] somewhere, which would raise KeyError. It's a maintenance hazard.

What to do: Wrap the boundaries in an accessor method that handles conversion, or define a named constant for the string conversion. The simplest fix is a small helper:

def get_boundary(boundaries, grade):
    """Fetch a grade boundary by integer grade, handling the JSON string-key format."""
    return boundaries[str(grade)]

Then replace every direct access. This makes the code self-documenting and prevents the KeyError entirely.

SC3 — Edge Case in calculate_required_score() When There Are Zero Assessments

What's wrong now: If a student has just set up a course but hasn't added any assessments yet:

n = len(assessments)  # = 0
existing_total = sum(...)  # = 0
required = target_min * (0 + 1) - 0  # = target_min

This actually works correctly — it returns target_min as the required score for the first assessment, which is exactly right. Good.

But: view_course_details() calls print_summary_for_course(), which calls calculate_required_score() even when assessments is empty. Test this path — it should display "Need 90% on your next assessment for grade 7" which is correct and helpful.

What to do: Add a test for this. Confirm the output is correct. Mention it in Criterion D as evidence of handling the empty-collection case.

Precision — calculate_grade() Uses Floating-Point Comparison

What's wrong now: In calculate_grade():

if average >= boundaries[str(grade)]:
    return grade

If average is computed as 89.99999999 due to floating-point arithmetic, and the boundary for grade 7 is exactly 90, this returns grade 6 — which is correct but surprising to the user who sees "90.00%" displayed.

Why it matters: This is a classic floating-point trap. It's unlikely to occur in practice with two decimal places, but a student who has exactly 90.00% displayed and is told they have a 6 is going to be confused.

What to add: Round the average to a small number of decimal places before comparing:

def calculate_grade(average, boundaries):
    if average is None:
        return None
    average = round(average, 2)
    for grade in GRADES:
        if average >= boundaries[str(grade)]:
            return grade
    return None

How to test it: Add assessments that produce exactly 90.00% average and confirm the grade is 7, not 6.

Display — Course Name Truncation May Cut Off Important Words

What's wrong now: In view_all_courses():

display_name = name if len(name) <= name_width - 1 else name[:name_width - 4] + "..."

With name_width = 30, this truncates anything over 29 chars to 26 chars + "...". Long names like "Mathematics: Analysis and Approaches (AA)" will become "Mathematics: Analysis a..." — cutting off the crucial (AA) vs (AI) distinction.

Why it matters: The two Math courses are the ones most likely to be confused. Truncating them so they look identical defeats the purpose of the display.

What to add: Either widen the column, or add a numeric ID next to each course so users can distinguish them:

# Option A: widen the column
name_width = 45

# Option B: show an index
for i, (name, course) in enumerate(data["courses"].items(), start=1):
    # print with i as prefix so users can refer to "course 3"

Robustness — Save Errors Are Not Caught

What's wrong now: save_data() has no error handling:

def save_data(data):
    with open(DATA_FILE, "w", encoding="utf-8") as f:
        json.dump(data, f, indent=2, ensure_ascii=False)

If the disk is full, or the file is locked by another program, or the directory becomes read-only, the app crashes and the user loses all unsaved work.

Why it matters: SC7 is about preventing crashes. Robustness in persistence is a natural extension of that.

What to add:

def save_data(data):
    try:
        with open(DATA_FILE, "w", encoding="utf-8") as f:
            json.dump(data, f, indent=2, ensure_ascii=False)
        return True
    except OSError as error:
        print(c(f"  Could not save data: {error}", ERR_C))
        return False

Then check the return value wherever you call save_data() and warn the user if it fails.

🏗️ OOP Refactor — Why and How

The current code is entirely procedural — 12 functions with no classes. This is the biggest structural gap for Criterion D. Criterion C explicitly says: "For object-oriented coding, it is important to document the component objects using UML diagrams that show dependencies between objects." With no classes, you have no UML diagram.

Current Structure (Procedural)

+---------------------------------------------+ | ib_score_tracker.py | | (~400 lines of functions) | +---------------------------------------------+ | load_data() / save_data() | | input_int() / input_float() | | input_nonempty() / pause() | | choose_subjects() / setup_courses() | | edit_course_settings() | | select_course() | | add_assessment() / edit_assessment() | | delete_assessment() | | calculate_average() / calculate_grade() | | calculate_required_score() | | view_course_details() / view_all_courses() | | print_summary_for_course() | | print_menu() / main() | +---------------------------------------------+

Proposed Structure (OOP)

Extract three classes, each with a single responsibility:

+-----------------------------+ | CourseTracker | | (top-level controller) | +-----------------------------+ | - data: dict | | - store: DataStore | +-----------------------------+ | + setup_courses() | | + add_assessment() | | + edit_assessment() | | + delete_assessment() | +------+---------------+------+ | | | uses | uses v v +----------------+ +-------------------+ | DataStore | | Course | | (JSON I/O) | | (model) | +----------------+ +-------------------+ | + load() | | - name | | + save(data) | | - boundaries | +----------------+ | - target_grade | | - assessments | +-------------------+ | + average() | | + grade() | | + required_score()| +-------------------+

Why This Helps

  • Criterion C — a UML diagram becomes natural to draw
  • Criterion D — you can show clean code excerpts of each class and justify the separation
  • Testability — you can write course = Course("Maths AA", boundaries, 7); assert course.average() == 85.0 without running the CLI
  • Extensibility — if you later want a GUI, only CourseTracker changes; Course and DataStore stay the same

Example Skeleton

class Course:
    def __init__(self, name, boundaries, target_grade):
        self.name = name
        self.boundaries = boundaries
        self.target_grade = target_grade
        self.assessments = []

    def average(self):
        if not self.assessments:
            return None
        return sum(a["score"] for a in self.assessments) / len(self.assessments)

    def grade(self):
        avg = self.average()
        if avg is None:
            return None
        avg = round(avg, 2)
        for g in GRADES:
            if avg >= self.boundaries[str(g)]:
                return g
        return None

    def required_score(self):
        target_min = self.boundaries[str(self.target_grade)]
        n = len(self.assessments)
        existing = sum(a["score"] for a in self.assessments)
        required = target_min * (n + 1) - existing
        if required <= 0:
            return ("already_secured", 0)
        if required > 100:
            return ("impossible", (existing + 100) / (n + 1))
        return ("possible", required)
