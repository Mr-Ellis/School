! The biggest mistakes you could make

Letting the language become too computer-science heavy

This is the largest issue. Some passages use terms that sound impressive but make the paragraph harder to follow than the implementation actually is. Moderators reward clear technical explanation more than advanced-sounding terminology. Ask yourself: could the client understand this paragraph? If the answer is “probably not”, simplify it.

Examples of terms that need justifying or simplifying:

  • hardware performance counters (TSC, HPET)
  • GIL contention
  • B-tree latency
  • deterministic finite automata
  • open addressing hash tables

Making performance claims that look overconfident

Statements like “under 1.5 ms”, “under 5 ms” and “O(1) lookup <0.05 ms” sound precise, but the code does not appear to provide rigorous evidence for every exact value. Moderators generally prefer an honest measured range to a claimed guarantee.

Instead of: “This will always be less than 5 ms.”
Write: “Testing showed average latency between X and Y ms over N runs.”

Using absolute wording for theoretical claims

Nothing in IB moderation is really “perfect”. Safer wording — “effectively demonstrates”, “provides evidence that”, “strongly suggests” — is both more accurate and more convincing to a moderator.

1

Entropy calculation

The entropy engine implements the formula E = L × log₂(R), calculating password entropy from length and character-set size in the calculate_entropy() function. This is a genuine mathematical model, not a lookup table.

The write-up already discusses the limitation — entropy assumes randomness and therefore needs correction mechanisms for predictable passwords. Keep that discussion, and make sure the correction mechanisms are explained as part of the same technique rather than as a separate feature.

This is the clearest example of the project applying a mathematical model rather than pattern-matching alone.
2

Brute-force cracking model

The cracking model estimates how long a password would take to crack under a given guess rate. It turns entropy into a user-facing estimate and is the part of the system most likely to be questioned, so the assumptions need to be explicit.

Make sure the write-up states the guess rate used, why that rate was chosen, and what a realistic alternative would be. That is the evaluation the moderator is looking for.

The cracking model is where evaluation matters most — the assumptions are the technique.
3

Hash-based breach detection

Breach detection uses a Python set of hashed passwords and looks up the candidate password's hash in constant time. The write-up already notes the trade-off: local breach datasets improve privacy but cannot remain fully up to date, and set lookups are faster but consume memory.

Keep both halves of that trade-off explicit. They are exactly the kind of evaluation moderators reward.

The privacy-versus-recency trade-off is a real design decision, not a description of what a set is.
4

Regex pattern detection

Repeat detection uses the regular expression r'(.)\1{2,}' to find repeated character sequences. Keyboard-walk and sequence detection use sliding-window analysis rather than regex alone.

The write-up already notes that QWERTY detection excludes other keyboard layouts. That is a good limitation — keep it, and explain why the exclusion was acceptable for the intended users.

The layout limitation is a strong evaluation point; the detection method itself is the technique.
5

Sequence detection

Sequence recognition detects keyboard walks, alphabet sequences and number sequences using sliding-window analysis. It is one of the more complex pieces of pattern logic in the project.

Show this in the video with a passphrase that contains a recognisable sequence and one that does not — the contrast makes the algorithm visible.

Sequence detection is the technique most likely to be under-explained in the write-up and most impressive when demonstrated.
6

Penalty engine

The penalty engine applies deductions to the raw entropy score for detected weaknesses. It is the part of the system that turns independent detection results into a single judgement.

Make sure the write-up explains how the penalties combine — whether they are additive, capped, or weighted — and why that combination was chosen over the alternatives.

The combination rule is a genuine design decision; describing it as “penalties are applied” is not.
7

Boundary validation

Boundary validation checks that inputs fall within expected ranges before they are used by the rest of the pipeline. It is the source of most of the abnormal testing in the project.

In the write-up, make the order of checks explicit and show what happens when each one fails. That is the difference between describing validation and demonstrating it.

Validation is easy to under-explain — the sequence of checks and the failure behaviour are what matter.

2 Structure for each technique

Use this structure for every technique. Points F, H and I are the evaluation and justification points — those are what push a report from 9–11 into 11–12. The examples below use the hash-based breach detection technique.

A

What is the technique?

Explain the technique in one or two sentences, independent of your project.

“Hash-based breach detection stores known breached passwords as hashes in a set, so a candidate password can be checked in constant time without storing the plaintext passwords.”
B

How is it used in my solution?

Connect the technique directly to your project.

“When a password is entered, its hash is looked up in the local breach set; if it is found, the password is flagged as compromised.”
C

Why did I choose it?

Give the computational reason, not just the user-facing benefit.

“A set lookup is O(1) on average, so checking against a large breach list does not slow the analysis down.”
D

What alternative could I have used?

Name a realistic alternative and say what is wrong with it.

“A live online breach API would be more up to date, but it would require a network connection and would send the password to a third party.”
E

What is a limitation?

Every technique has one. Naming it honestly strengthens the evaluation.

“The local dataset cannot remain fully up to date, and the set consumes memory proportional to the number of stored hashes.”
F

Why is my choice still appropriate? (evaluation)

Weigh the limitation against the benefit and reach a judgement.

“Although the dataset cannot be perfectly current, local hashing keeps passwords private and the memory cost is acceptable for the intended dataset size.”
G

How did I test it?

Describe the normal, abnormal and extreme cases you actually ran.

“I tested a known breached password, a known safe password, an empty input, and a lookup against a breach set of 10,000 hashes.”
H

Why was the testing effective? (justification)

Explain what the tests prove — not just that they were run.

“The normal tests confirmed known-breach and known-safe passwords are classified correctly, and the extreme test showed the lookup remained fast with a large breach set, which supports the O(1) design claim.”
I

What does the testing NOT prove? (evaluation of testing)

Name what remains unproven. This is the point most students skip.

“The tests confirm the lookup works on the dataset I used, but they do not prove the system would detect a password that has been breached since the dataset was last updated.”

E Evaluation checklist

The implementation sections already evaluate well. Use this to confirm nothing has slipped, especially for the testing discussion.

  1. I discussed at least one alternative for each major technique.
  2. I discussed the advantages of my chosen approach.
  3. I discussed the limitations of my chosen approach.
  4. I explained why the advantages outweigh the limitations.
  5. I explained what the testing demonstrates.
  6. I explained what the testing does not prove.
The quick evaluation test: if a paragraph can be rewritten as “I used X because it does Y”, it is probably explanation. If it includes an advantage, a limitation, an alternative and a trade-off, it is probably evaluation.
