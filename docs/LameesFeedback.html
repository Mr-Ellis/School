1. Techniques to Justify

No fixed number is required. The rubric asks for appropriate techniques, judged on quality, not counted. For your project, six to nine is the right range. You already have nine in your code.

Do not pad the list with basic syntax. Loops, print(), comments, and file names do not count as techniques. A technique earns a paragraph only when another programmer might have solved it differently.

2. How to Write Each Technique

Aim for 100 words per technique, using the same five-point structure:

  1. What the technique is
  2. Where in your code it appears
  3. Why you chose it
  4. What benefit it gives the user
  5. What limitation it has

Point five is what most students skip. It is also what turns a description into an evaluation, which is what the top band requires.

5. Required Code Changes

5.1 Fix the SC8 / SC9 duplication in Criterion A

SC8 and SC9 in Criterion A use identical wording. Decide what SC9 should actually say. Two possibilities that match the current code:

  • "The system allows the user to delete a previously entered record." — but this would require adding delete functionality that is not currently implemented
  • "The system allows the user to view all records without a date range filter." — already implemented by App.all_records() but not stated as a success criterion

The cleanest fix is to make SC9 a criterion the code already satisfies. Choose one of the above and update Criterion A so the wording matches what the code actually does.

5.2 Executable is already built

The program has already been packaged as a standalone executable, which is an advantage: the client can run it without installing Python. Before recording, confirm the .exe was built from the current version of the source, and test it on a machine that does not have Python installed. If any code changes are made after the build, rebuild with:

pyinstaller --onefile --windowed --name "JuliaHabitTracker" JuliaHabitTracker.py

Notes for the rebuild if needed:

  • --onefile produces a single .exe
  • --windowed hides the console, correct for a GUI-only app
  • The SQLite database is created at runtime in Documents/JuliaHabitTracker/data/, so no data files need to be bundled
  • Test the final .exe on a clean machine — the database folder should still be created automatically

5.3 Mood edit currently updates every habit on that date — this is intentional but should be labelled

Editing a mood score changes it for every habit record on that day. This is correct behaviour given the schema, because mood is stored in the moods table keyed by day. The UI makes this clear with the label "One mood score per day. Saving a mood updates every habit on that date." — keep this label visible in the video. It is a deliberate design decision worth justifying in the write-up.

5.4 The report box does not refresh after an edit

When a record is edited and saved, the table updates but the report box (streaks, trends, feedback) is not recalculated. The simplest fix is to call self.refresh() at the end of App.save() — it already refreshes the table, and adding a call to self.update_report(records) after refresh() would update the report too. In practice, refresh() already calls update_report(), so the issue is likely that the report is not re-rendered after the edit path. Check the flow through App.save() and App.refresh().

If the report does not need to update after every edit for the client's workflow, that is acceptable. But state it in the write-up as a known limitation: "the trend report is recalculated on search, not on edit."

5.5 SC9 — Client evidence and splash guidance

Send the client a Microsoft Forms survey with one Likert question per SC. Record the responses and reference them in the video. Add the splash dialog described in Section 7 so the interface is self-explanatory on first launch.

5.6 Default date range hides recent data

The default start date is 29 days ago, so a record from 60 days ago is hidden until the user clicks "All records". The status message tells the user this, which is good. Consider setting the default range to cover a full year, or adding "Last 30 days" / "Last 90 days" quick-select buttons.

5.7 The trend threshold values are not justified

trend_label(change, threshold) uses 0.5 for mood and 10 for completion. These are reasonable but arbitrary. State in the write-up where they come from, or acknowledge they are approximations chosen to avoid classifying noise as a trend. That turns a magic number into a justified decision.

7. Splash Screen

A splash screen supports SC9 and provides a screenshot for the Criterion C wireframe. Keep it short.

7.1 Where to add it

In App.__init__, after the layout is built, call self.show_splash() once. Add a "Help" button to the search bar so the dialog can be re-displayed at any time.

7.2 The splash function

def show_splash(self):
    splash = tk.Toplevel(self.root)
    splash.title("Welcome")
    splash.geometry("460x320")
    splash.transient(self.root)
    splash.grab_set()

    ttk.Label(
        splash,
        text="Julia • Habits & Mood",
        font=("Helvetica", 16, "bold")
    ).pack(padx=24, pady=(24, 6), anchor="w")

    ttk.Label(
        splash,
        text=(
            "Track your habits, reflect on your mood, and see\n"
            "your progress over time.\n\n"
            "HOW TO USE\n"
            "  1. Fill in the daily check-in form and press Save.\n"
            "  2. Use the date range to search past records.\n"
            "  3. Read the report below the table for streaks,\n"
            "     trends, and personalised feedback.\n\n"
            "Your data stays on this computer."
        ),
        justify="left",
        wraplength=420
    ).pack(padx=24, pady=(0, 16), anchor="w")

    ttk.Button(
        splash,
        text="Got it",
        command=splash.destroy
    ).pack(padx=24, pady=(0, 24), fill="x")

8.4 Immediate priority

The most urgent item is the SC8 / SC9 duplication in Criterion A. Two of your ten success criteria say the same thing. An assessor will notice this immediately and it reduces the mark in Criterion A. Decide what SC9 should be and update Criterion A so the wording matches the code.

The second priority is confirming the existing executable was built from the current version of the source and testing it on a clean machine. The database is created at runtime, so once the .exe runs, SC9 and SC10 are demonstrable.

The third priority is the report-box refresh after an edit. If the trend report does not recalculate when an existing record is changed, either fix it by calling self.refresh() at the end of App.save(), or state in the write-up that the report recalculates on search only. Both are acceptable, but the behaviour must be documented.
