SQLite relational database design model — rewrite

Rewrite in your own words and insert a screenshot of your schema.

What it is

The application stores its data in a relational SQLite database rather than a flat file. Three tables — habits, moods and entries — are linked by foreign keys, and the database enforces rules such as UNIQUE and CHECK constraints so that invalid records cannot be stored even if the program has a bug.

How it is used

Each habit has a row in habits. Each daily log entry has a row in entries that references a habit by foreign key and stores the completion state and mood. The UNIQUE(habit, day) constraint means the same habit cannot be logged twice on the same day, and the CHECK constraints on mood require a value between 1 and 10.

Why I chose it

The tracker needs to answer questions that span multiple days and multiple habits — streaks, trends and averages. A relational schema makes those queries short and lets the database engine do the filtering and joining, instead of loading everything into Python and looping over it.

Alternative considered

A single JSON file would have been simpler to write. However, it would have stored every habit and every entry in one flat structure, which makes streak and trend queries more fragile, and it would offer no protection against duplicate entries for the same habit and day.

Limitation

SQLite adds setup complexity. The schema has to be created before the application can run, and changing a table's structure later requires a migration rather than simply adding a key to a dictionary. It also introduces a second place where errors can occur — a constraint violation is a runtime failure the program must handle.

Why it is still appropriate

Although a JSON file would have been faster to prototype, the relational design pays for itself as soon as the program needs to answer multi-day questions. The constraints turn data-integrity rules into something the database enforces rather than something the program has to remember to check.

A moderator sees a real schema with real constraints, not a GUI with a save button. This is the strongest technique in the project.

Input validation and data integrity model — rewrite

Rewrite in your own words and show the order of checks.

What it is

Validation is the set of checks that run before data is written, so that invalid input is rejected instead of being stored. In this application it happens at two layers: in the Python code, and in the database schema itself.

How it is used

The Python layer checks that the date is a real date, that it is not in the future, that the mood is an integer between 1 and 10, and that the habit name is a sensible length. The database layer then enforces the same rules again through CHECK constraints and the UNIQUE(habit, day) constraint, so a duplicate entry is rejected even if the Python check is bypassed.

Why I chose it

Two layers of validation mean a single mistake in the program code does not automatically corrupt the data. The Python layer gives the user a friendly error message; the database layer guarantees the invariant.

Alternative considered

Validation could have been done only in Python. That is simpler, but it means the integrity of the data depends entirely on the code being correct. Since SQLite enforces constraints for free, there was no good reason not to use them.

Limitation

The two layers duplicate some rules, so changing a rule means changing it in both places, and they can drift out of sync. The database also produces less friendly error messages than the Python layer, so the program has to catch constraint violations and translate them.

Why it is still appropriate

For a small application the duplication is minor, and the benefit — guaranteed data integrity — outweighs the maintenance cost. The Python layer handles the user experience and the database layer handles the correctness, which separates two concerns rather than tangling them.

Multi-layer validation is stronger than the single-layer validation most students write about, because it shows you understand the difference between checking for the user and guaranteeing the data.

Streak calculation algorithm model — rewrite

Rewrite in your own words and insert a screenshot of the streak function.

What it is

A streak is the number of consecutive days on which a habit was completed. The algorithm computes two values: the current streak, counting backwards from today, and the best streak, which is the longest run anywhere in the record.

How it is used

The program first collects every day on which the habit was marked complete and converts that list into a set. It then starts at today and walks backwards one day at a time, incrementing a counter while each day is in the set and stopping at the first day that is not. The best streak is found by walking the complete sorted list of completed days once and tracking the longest consecutive run.

Why I chose it

Converting the days to a set makes each "was this day completed?" check an O(1) membership test instead of a scan through a list. The backwards walk is then O(n) in the length of the streak, which is exactly the work that needs to be done and nothing more.

Alternative considered

A list could have been used and searched each time, but every step of the backwards walk would then be a linear search, making the whole streak calculation quadratic in the number of entries. A set makes the same algorithm linear.

Limitation

The algorithm assumes that a day is either complete or not — it cannot represent a habit that was partially completed, and it treats a missed day as a hard reset. It also depends on the system clock: if the computer's date is wrong, the current streak will be wrong.

Why it is still appropriate

For a habit tracker, "completed or not" is exactly the right model, and a missed day genuinely should reset the current streak — that is what makes the streak motivating. The clock dependency is a real risk, but it is a property of the platform rather than of the algorithm.

This is a genuine algorithm — set conversion, backwards iteration and date arithmetic — and one of the three strongest pieces of computational thinking in the project.

Trend classification algorithm model — rewrite

Rewrite in your own words and insert a screenshot of trend_description().

What it is

Trend classification compares two windows of time and reports whether the user's habits are improving, stable or declining. It is a simple form of time-series analysis, done without any external library.

How it is used

The function takes the last 7 days and the previous 7 days, and calculates two deltas: the change in average mood and the change in completion rate. It then classifies the result as improving if both deltas are positive beyond a threshold, declining if both are negative beyond a threshold, and stable otherwise.

Why I chose it

Two windows of equal length give a fair comparison, and reducing the trend to two numbers — mood change and completion change — keeps the output easy to explain to the user. It also means the classification rule is visible in the code rather than hidden inside a model.

Alternative considered

A linear regression over all recorded days would have produced a more statistically rigorous trend. However, it would require more code, it would be harder to explain in the interface, and with only a few weeks of data the regression would be dominated by noise anyway.

Limitation

The thresholds are chosen by hand rather than derived from the data, so the boundary between "stable" and "improving" is arbitrary. The comparison also ignores how much data is available — a 7-day window with only two entries is treated the same as a 7-day window with seven.

Why it is still appropriate

For a personal tracker the goal is a useful signal, not a statistically valid one, and a simple two-window comparison gives that signal with far less code and far more transparency than a regression would. The arbitrary threshold is a known cost, and it is one the user can understand.

This is the most sophisticated piece of analysis in the project, and it deserves a full section rather than a passing mention.
5

Summary statistics algorithm model — rewrite

Rewrite in your own words. This is the shortest of the six sections.

What it is

Summary statistics reduce the whole record to two numbers: the average mood across all logged days and the completion rate across all logged entries. They give the user a single view of overall progress.

How it is used

The program queries the entries table, counts the completed entries and divides by the total number of entries to get the completion rate, and averages the non-null mood values to get the average mood. Both calculations are done in SQL rather than in Python.

Why I chose it

Doing the aggregation in SQL means only the two resulting numbers are moved into Python, rather than every row. It also keeps the calculation in one place instead of scattering it across the user-interface code.

Alternative considered

The averages could have been stored as columns and updated every time an entry was added. That would be faster to read, but it would introduce the risk of the stored value going stale if an entry were ever edited or deleted, and it would duplicate information the database can derive.

Limitation

An arithmetic mean gives every day equal weight, so a single unusually bad day and a single unusually good day can cancel out. The completion rate also treats every habit equally, regardless of how often it was supposed to be done.

Why it is still appropriate

For a summary display the arithmetic mean is exactly what the user expects, and recalculating it on demand means it is always consistent with the underlying data. The equal-weighting limitation is real, but a weighted average would need a scheme for deciding the weights, which would add complexity for a summary statistic.

Not as strong as streaks or trends, but still a valid technique, and the "why not store it" discussion is genuine evaluation.
6

Motivational feedback generation model — rewrite

Rewrite in your own words and insert a screenshot of motivational_feedback().

What it is

Feedback generation turns the computed values — mood, completion rate and streaks — into a short message for the user. It is a rule-based decision system rather than a fixed string.

How it is used

The function takes the current streak, the completion rate and the trend classification, and selects a message based on which combination of conditions is true. A long streak with a declining trend produces a different message from a short streak with an improving trend, and the rules are arranged in priority order so that the most important condition is checked first.

Why I chose it

A rule-based approach keeps the logic visible and testable. Each rule can be checked independently, and the user can be told exactly why a message was chosen.

Alternative considered

A random selection from a pool of messages would have been simpler, but it would not respond to the user's actual data, and it would make the application feel less personal. A language model would have produced more varied feedback, but it would have introduced a dependency, a cost and a loss of control over the tone.

Limitation

The rules are hand-written, so the feedback is limited to the situations the author anticipated. It cannot recognise a pattern the author did not think of, and the priority order means a low-priority rule can be permanently masked by a high-priority one.

Why it is still appropriate

For a personal habit tracker, predictable and explainable feedback is more valuable than variety, and a rule-based system gives exactly that. The limited range of messages is a fair trade for the transparency of being able to see why each one was chosen.

Decision logic based on three computed values is still decision logic, and it links the earlier algorithms to the user-facing outcome.

Extreme testing is separate: it confirms that valid input at the edge of the program's limits — long streaks, many habits, a year of entries — is still handled correctly.
