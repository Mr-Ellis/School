1. How Many Techniques?

There is no fixed number. The rubric asks for appropriate techniques, judged on quality, not counted. For a project your size, six to nine is the right range.

The top band asks for three things:

  • Appropriate techniques — the right tool for the job
  • Evaluation of why each was chosen
  • Justification of the testing strategy

"Appropriate" means the technique fits the problem. A dictionary is right for a lookup. A loop is right for repeated validation. A regular expression would be wrong for a simple range check — correct tool, correct context.

All of these are already in your code. You do not need to add anything to reach a strong list. You need to write them up.

One refactor unlocks an eighth technique:

You do not need both. Classes is the stronger choice — it also strengthens Criterion C, because you gain concrete structure to diagram.

What not to include

Do not pad the list with basic syntax. These do not count as techniques:
  • "I used a for loop to iterate a list"
  • "I used print() to show output"
  • "I used comments to document my code"
  • "I used a Python file"

A technique earns a paragraph when it is a deliberate design choice another programmer might have solved differently. Dictionaries versus lists. JSON versus SQLite. Pure functions versus classes. Those are real choices.

2. How to Write Each Technique

Aim for 80–120 words per technique, in the same five-point structure every time:

  1. What the technique is
  2. Where in your code it appears
  3. Why you chose it
  4. What benefit it gives the user
  5. What limitation it has

Point five is the part most students skip. It is also the part that separates a description from an evaluation, which is what the top band asks for.

4. Required Changes

4.1 Storage consistency

Criterion B describes a SQLite storage system. The implementation uses JSON. The assessment criteria require development to be consistent with planning. Two options exist:

  • Option A: Refactor the storage layer to use SQLite. The sqlite3 module is part of the Python standard library.
  • Option B: Rewrite the storage component in Criterion B to describe JSON, and justify the choice (readable, portable, no schema migration).

One of these must be completed. An inconsistency between Criterion B and Criterion D reduces the mark in both criteria.

4.2 Object-oriented refactor

The program is currently procedural. Introducing classes provides concrete structural decisions to justify. Suggested classes:

  • Assessment — stores name, score, and date
  • Subject — stores name, boundaries, target grade, and a list of Assessment objects; provides average(), current_grade(), and required_next() methods
  • Tracker — stores all Subject objects and handles load and save operations

This is the largest available mark gain for Criterion D.

4.3 SC5 — Table format

The aligned table in print_assessment_list() is not used by show_subject_detail(). Replace the list output in show_subject_detail() with a call to the table function.

4.4 SC10 — Explicit message

In show_subject_detail(), when the assessment list is empty, print "Not enough data to predict — add at least one assessment." and return before attempting prediction.

6. Strengths of the Implementation

The following aspects of the project are technically sound and should be justified in the Criterion D write-up.

6.1 Separation of logic and interface

The project separates calculation logic (ib_score_tracker.py) from user interaction and file handling (main.py). Each calculation function can be tested in isolation, and a bug in the menu system cannot corrupt the calculation logic.

6.2 Boundary normalisation

normalize_boundaries() converts string-keyed JSON boundaries into integer-keyed dictionaries, backfills missing IB levels with defaults, and skips invalid keys. The save file format can evolve without breaking existing data.

6.3 Three-case prediction algorithm

calculate_next_score_requirement() correctly handles three distinct cases: target already secured (returns 0), target reachable (returns required percentage), and target impossible (returns None).

6.4 Robust data loading

load_data() catches JSONDecodeError and OSError, backfills missing top-level keys, and normalises nested data. A corrupted save file does not cause a crash.

6.5 Loop-based validation

Validation in add_assessment() and edit_subject_boundaries() repeats the prompt on invalid input rather than exiting. This is the correct behaviour for a menu-driven program.

8. Criterion D Write-Up Structure

The write-up should follow the structure below. Total length approximately 1,000 words.

Part 1 — Structure justification (approximately 200 words)

Explain and justify:

  • The two-file separation between logic and interface
  • The choice of JSON or SQLite
  • The procedural or object-oriented design

Every sentence should answer "because". Description alone does not meet the requirement.

Part 2 — Techniques used (approximately 600 words)

Provide one subsection per technique from Section 1. Each subsection must cover the five points listed in Section 2. Techniques may be grouped where they relate to the same area, but each must still be evaluated.

Part 3 — Testing strategy (approximately 200 words)

Address the following:

  • Why valid, invalid, and extreme categories were chosen
  • Why these specific test cases
  • Which tests failed and what was changed as a result
  • How each test links to a success criterion
  • Where each test appears in the video, by timestamp
