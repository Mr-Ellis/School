1. Techniques to Justify

No fixed number is required. The rubric asks for appropriate techniques, judged on quality, not counted. For your project, six to nine is the right range. You already have ten in your code.
Technique Where it appears Strength
1 Class-based structure — HomeworkManager holds all state (tasks, selected_task_id) and methods homework_task_manager.py, whole file Strong
2 Priority calculation algorithm — converts a due date into a tier (Overdue, Urgent, High, Medium, Low) and a numeric score calculate_priority() Strong
3 Compound sort key — tasks are sorted by priority score, then due date, then title, so ties are resolved consistently sort_tasks() Strong
4 Automatic priority refresh on a timer — the app recalculates days-left and priority every 60 seconds without user action auto_refresh(), root.after(60000, ...) Strong
5 JSON persistence with safe loading — bad JSON falls back to an empty list and shows an error rather than crashing load_tasks(), save_tasks() Strong
6 Validation with date format checking via datetime.strptime validate_input() Moderate
7 Event-driven UI with tkinter.ttk — a Treeview bound to selection, so clicking a row loads it into the form tree.bind("<<TreeviewSelect>>", ...), select_task() Strong
8 Confirmation dialogs for destructive actions delete_task(), messagebox.askyesno Moderate
9 Auto-incrementing IDs — new tasks receive max(existing ids) + 1 get_new_id() Moderate
10 Standalone packaging with PyInstaller — the program runs as a distributable .exe without Python installed on the client machine Build step, not source code Strong

Do not pad the list with basic syntax. Loops, print(), comments, and file names do not count as techniques. A technique earns a paragraph only when another programmer might have solved it differently.

2. How to Write Each Technique

Aim for 100 words per technique, using the same five-point structure:

  1. What the technique is
  2. Where in your code it appears
  3. Why you chose it
  4. What benefit it gives the user
  5. What limitation it has

Point five is what most students skip. It is also what turns a description into an evaluation, which is what the top band requires.

5. Required Code Changes

5.1 Confirm the executable is up to date

The program has already been packaged as a standalone executable, and it opens when double-clicked. Before recording, confirm the .exe was built from the current version of the source. If any code changes are made after the build, rebuild with:

pyinstaller --onefile --windowed --name "HomeworkTaskManager" homework_task_manager.py

Notes for the rebuild if needed:

  • --onefile produces a single .exe
  • --windowed hides the console window, correct for a GUI-only app
  • The JSON file is created in the working directory at first run, so nothing needs to be bundled
  • Test the final .exe on a clean machine without Python installed — the JSON file should be created alongside the .exe the first time the client saves a task
  • If a rebuild produces an Ordinal Not Found error on the target machine, rebuild with --onedir and install the Visual C++ Redistributable there

5.2 Test data in homework_tasks.json

The current JSON file contains one sample record with due date 1999-12-26, which the program correctly classifies as OVERDUE with days_left: -9783. This record was added during development to confirm that saving and reloading worked.

When you record the video, use the "Delete Task" button to remove this sample entry first, then add realistic tasks for the demonstration. That gives a clean starting state and lets the assessor see the empty table before any real data is entered. Keeping the sample record in the file is fine for the written submission, but the video should start from a state the client would recognise.

5.3 Editing an overdue task keeps it overdue until the next refresh

When a task is edited, edit_task() calls calculate_priority() again on the new due date, so priority is recalculated correctly. However, the "OVERDUE" tag remains until the next refresh if the edit form is used on a task whose due date is still in the past. This is correct behaviour. State it clearly in the write-up so an assessor does not mistake it for a bug.

5.4 Days-left display when the JSON is edited externally

In refresh_task_list(), negative days_left is displayed as "X day(s) late", which is correct. But if the JSON is manually edited and days_left is a string instead of an integer, the display falls through to str(days_left) and shows the raw string. This is not a bug in normal use — the JSON is always written by save_tasks(). Note it as a limitation if you want.

5.5 No splash / welcome screen

The UI is functional but has no guidance for a first-time user. Add a splash or welcome message at startup that explains the three core actions: add, edit, delete. This supports SC9 (usability) and gives you a screenshot for the Criterion C wireframe. See Section 7 for a starter implementation.

5.6 The auto-refresh interval is not justified

The program recalculates priorities every 60 seconds (root.after(60000, self.auto_refresh)). This is reasonable but arbitrary. State in the write-up where the value comes from — for example, "a minute is long enough that a student will not notice stale priorities, but short enough that leaving the program open overnight still updates the display." That turns a magic number into a justified decision.

5.7 Criterion A does not name a real client

Your Criterion A refers to "Students" and "Maxim" but does not define a single client with subjects, year group, and specific problems. The assessment criteria require a specific client. Update Criterion A to name one real person, describe their homework load, and quote them about the problem. This is a Criterion A issue, but it also affects Criterion D because the video should show that client using the program.

7. Splash Screen

A splash screen supports SC9 and provides a screenshot for the Criterion C wireframe. Keep it short.

7.1 Where to add it

In HomeworkManager.__init__, after create_widgets(), call self.show_splash(). Add a "Help" button to the top of the window so it can be re-displayed at any time.

7.2 The splash function

def show_splash(self):
    splash = tk.Toplevel(self.root)
    splash.title("Welcome")
    splash.geometry("460x340")
    splash.transient(self.root)
    splash.grab_set()

    tk.Label(
        splash,
        text="Homework Task Manager",
        font=("Arial", 16, "bold")
    ).pack(padx=24, pady=(24, 6), anchor="w")

    tk.Label(
        splash,
        text=(
            "Keep track of your homework and see what needs\n"
            "your attention first.\n\n"
            "HOW TO USE\n"
            "  1. Fill in the form at the top and press Add Task.\n"
            "  2. Tasks are sorted so the most urgent are at the top.\n"
            "  3. Click a row to load it, then edit or delete it.\n"
            "  4. Priorities update automatically as deadlines pass."
        ),
        justify="left",
        font=("Arial", 10),
        wraplength=400
    ).pack(padx=24, pady=(0, 16), anchor="w")

    tk.Button(
        splash,
        text="Got it",
        width=15,
        command=splash.destroy
    ).pack(padx=24, pady=(0, 24), fill="x")
