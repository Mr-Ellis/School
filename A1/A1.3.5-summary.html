💡 The Big Idea — The Illusion of Parallelism

A typical processor core does one thing at a time. Yet your machine appears to run a browser, a music player and a download at once.

This illusion of parallelism comes from the OS switching between tasks many times a second, giving each a short turn. For each switch, the OS:

  1. Saves the running task's state (its registers, memory pointers and open files)
  2. Restores the next task's state
  3. Hands over the CPU
This switching is pure overhead. Doing too much of it wastes the CPU it is meant to share.

To keep everything progressing, the OS acts as the coordinator for every resource: processor time, memory and I/O devices. Three challenges make that hard.

⏱️Task Scheduling
Deciding which process runs next, and for how long.
With many tasks competing, the system must keep choosing which runs next — using the algorithms from A1.3.3 (FCFS, Round Robin, Priority, Multilevel Queue).

The goal: keep interactive tasks responsive without starving background work.
⚔️Resource Contention
Two or more tasks want the same resource at the same time.
Tasks often want the same region of memory, the same file, or the same device — at the same time. The OS must arbitrate, which means some tasks wait.

Poorly handled: contention causes long delays, or lets a high-priority task get stuck behind a lower one holding what it needs.
🔒Deadlock
Progress stops entirely — each process waits for the other.
Contention can reach a state where progress stops completely. Process P1 holds resource R1 and asks for R2, while P2 holds R2 and asks for R1. Each waits for the other to release what it holds — and neither ever will.

This is a circular wait — the classic cause of deadlock.

🌀 Deadlock — The Circular Wait

P1 holds R1 ──waits for──▶ R2 held by P2
P2 holds R2 ──waits for──▶ R1 held by P1

Neither process can proceed. Neither will ever release what it holds.

The Four Necessary Conditions

Deadlock can occur only when all four conditions hold at the same time. Because all four are required together, the OS can prevent deadlock by denying any one of them.

ConditionWhat it means
1. Mutual exclusionA resource cannot be shared — only one process can use it at a time.
2. Hold and waitA process is holding at least one resource while waiting to acquire another.
3. No preemptionA resource cannot be forcibly taken back from a process — it must be released voluntarily.
4. Circular waitA cycle of processes exists, each waiting for a resource held by the next one in the chain.

Deadlock Strategies

StrategyHow it works
PreventionDesign the system so that one of the four conditions can never hold. For example, impose a fixed order in which resources must be requested — this removes the possibility of a circular wait.
AvoidanceThe OS checks before allocating whether the allocation could lead to deadlock. The Banker's algorithm is the classic example — it only allocates if all processes can eventually complete.
DetectionThe OS periodically checks for stuck processes. If a cycle is found, recovery is triggered.
RecoveryBreak the cycle by stopping (aborting) one or more processes, or by reallocating resources differently.

🔐 Synchronisation — Three Tools

When multiple processes share resources, the OS uses synchronisation tools to enforce mutual exclusion — ensuring only one process accesses a critical section at a time.

🚦 Semaphores Click to flip
An integer variable incremented (signal) or decremented (wait) atomically.

Binary — value 0 or 1, acts as a lock.
Counting — any non-negative value, manages multiple instances of a resource.
🔒 Locks Click to flip
A lock ensures only one process uses a shared resource at a time.

Binary locks (mutexes) — one process at a time.
Readers-writer locks — many readers OR one writer.
📦 Monitors Click to flip
A container holding shared variables and the methods that operate on them.

When a process uses a monitor's method, the monitor is automatically locked. Condition variables let processes wait for events and notify others.

Semaphores in Action — Two Worked Examples

Binary Semaphore — Two processes writing to the same log file

  1. Semaphore initialised to 1 — the log file is available.
  2. Process A checks the semaphore. It's 1, so A sets it to 0 (locks the resource) and writes.
  3. Process B tries to write. Semaphore is 0, so B is blocked until A finishes.
  4. A finishes and sets the semaphore back to 1.
  5. B sets it to 0, writes, and sets it back to 1 when done.

Counting Semaphore — Three database connections shared by many processes

  1. Semaphore initialised to 3 — three connections available.
  2. Process A wants a connection. Value is > 0, so A decrements it to 2 and gains access.
  3. B and C do the same — value drops to 1, then 0.
  4. Process D requests a connection — value is 0, so D must wait.
  5. A finishes and increments the semaphore back to 1 — now D can proceed.

🔍 Scenario Explorer — What's Happening Here?

For each scenario, click the question to reveal what's going wrong (or right).

📝 Two programs try to write to the same file at the same time
  • Problem: a race condition — the file's contents become corrupted because both processes write interleaved bytes.
  • Solution: mutual exclusion. A binary semaphore or mutex lock ensures only one writer at a time. The second process blocks until the first releases.
🔒 Process P1 holds R1 and waits for R2 — while P2 holds R2 and waits for R1
  • Problem: this is a classic deadlock. Both processes are stuck in a circular wait — neither will release what it holds.
  • Fix: Prevention via resource ordering — force both processes to request resources in the same fixed order (say R1 first, then R2). That removes the possibility of the cycle forming.
⚠️ A low-priority background task holds a lock that a high-priority alarm task needs
  • Problem: this is priority inversion. The high-priority process is effectively blocked by a lower-priority one.
  • Effect: the system's response time becomes unpredictable — critical work waits behind unimportant work.
  • Fix: priority inheritance — the low-priority process temporarily inherits the priority of the higher one, so it can finish quickly and release the resource.
⚡ The OS switches between processes hundreds of times per second
  • What's happening: context switching — the OS saves the state of one process and restores another.
  • Cost: pure overhead. Time spent saving and restoring registers, updating the memory map, and flushing caches is time not spent on useful work.
  • Balance: the OS must switch often enough to feel responsive, but not so often that overhead dominates. This is why the Round Robin quantum must be tuned carefully.

📋 Reference — Multitasking Challenges Summary

ChallengeWhat it isHow the OS handles it
Context switching overhead Saving and restoring process states costs CPU time — this is pure overhead. Tune the quantum; avoid unnecessary switches. Too many switches reduce performance.
Resource contention Multiple processes compete for the same CPU, memory, file or device. Arbitrate access; use mutual exclusion via semaphores, locks and monitors.
Synchronisation issues Processes must coordinate access to shared data to avoid corruption. Semaphores, locks, monitors, condition variables. Enforce critical sections.
Resource starvation A process is constantly denied resources it needs. Ageing — gradually raise the priority of waiting processes.
Priority inversion A low-priority process holds a resource needed by a high-priority one. Priority inheritance — the holder temporarily inherits the higher priority.
Deadlock Progress stops because each process waits for a resource another holds. Prevention, avoidance, detection, recovery.
